# 产品需求规格

版本：1.1 · 日期：2026-09-09 · 状态：最终 Demo 与审计修订后的产品规范；真实实现及 Demo 缺陷修复待执行。

相关文档：[交互流程](02-user-flows-and-ui.md)、[开发路线](09-development-roadmap.md)、[原型证据](14-prototype-traceability.md)。

## 1. 产品定位

GCSA-AiLab 是本地优先的模型训练、后训练与运行工作台。用户围绕一个实际目标组织模型、数据、执行环境、实验、评测和产物，完成从准备到试用的连续任务，而不是在互不关联的工具页面之间搬运文件。

产品同时覆盖语言与多模态模型、图片模型、视频模型和音频模型。训练和生成不是两个相互割裂的产品：用户可直接试用已有模型，也可以从训练得到候选，再用同一套输入和配方比较效果。模型库承担选择、准备与运行入口；工作台承担当前任务；模型实验室承担专项处理；作品与素材承担内容复用。

## 2. 目标用户与关键任务

| 用户 | 当前困难 | 本产品要完成的任务 | 成功的可观察结果 |
| --- | --- | --- | --- |
| 本地模型使用者 | 参数和后端分散，不知道组合是否适用 | 选择模型与设备，调整上下文、思考与缓存并运行 | 能解释本次实际设置，结果保留输入与配方 |
| 模型微调开发者 | 数据、训练、评测和适配器来源容易混淆 | 使用明确的数据版本完成微调、评测、登记、试用 | 候选可追溯到源模型、数据和执行环境 |
| 多媒体创作者 | 图像、视频、声音之间难以接续 | 从素材生成图片，再生成镜头与配音 | 每一步有独立结果，工作流来源链完整 |
| 算法研究人员 | 多个实验不能公平比较，失败记录易丢失 | 蒸馏、合并、量化、转换或行为调整对照 | 各候选独立执行和评测，失败可复现 |
| 自有算力维护者 | 多硬件环境的驱动与引擎能力不透明 | 管理本机、服务器、云实例，检查适配组合 | 能区分可连接、可加载、可执行与已验收 |

### 2.1 核心用户故事

- 作为微调开发者，我希望先选择任务目标与数据，再确认 SFT + LoRA 等组合，避免把方法名称当成互斥类别。
- 作为本地用户，我希望关闭思考和限制上下文后看到实际生效的参数，而不是仅隐藏界面上的思考文本。
- 作为多媒体用户，我希望保存图片后直接带入视频，并在视频结果中找到来源图片。
- 作为研究人员，我希望原始失败实验保留，新尝试有独立编号，不能被“重试成功”覆盖。
- 作为设备维护者，我希望界面说明某项优化缺少什么，而不是把全部选项都显示为可用。
- 作为数据使用者，我希望自行记录来源和使用范围，AI 可以整理材料，但不替我作授权结论。

## 3. 产品目标与不纳入首期的范围

### 3.1 必须实现的目标

1. 任务闭环：准备 → 执行 → 检查 → 保存；训练进一步支持评测 → 登记候选 → 试用。
2. 配方可追溯：记录输入、模型版本、训练或运行参数、数据版本、环境和结果。
3. 本地优先：没有远程服务时，已经准备好的本地模型仍可完成适用的本地任务。
4. 多硬件可解释：可见设备、引擎、格式和版本限制，按验证记录显示能力。
5. 人工控制：AI 建议必须先预览，用户应用后才修改，执行必须是单独的用户动作。
6. 增量接入：保留四类产品结构，但按照真实可交付的模型与设备组合逐步实现。

### 3.2 不纳入首个内测闭环

- 从零预训练通用大模型和大规模跨机训练平台。
- 无人工确认的自主实验代理、自动云实例采购或自动对外发布。
- 自营数据交易结算、订单支付、结算分成、合同签署系统。
- 面向组织的完整多人协同、细粒度组织权限、企业 SSO。
- 承诺所有模型、所有硬件、所有精度和所有加速方法任意组合可运行。

这些边界不删除 Demo 中的产品入口。未实现的真实能力必须明确显示“待接入”或“待验证”，并给出可继续完成的路径。

## 5. 通用业务规则

### 5.1 对象归属

项目包含任务、配方、评测与作品引用。模型文件和公开数据文件可以在物理存储中去重，但项目可见性、来源声明和缓存范围不能由去重自动扩大。后台任务提交时固定归属，完成时不能根据当前页面的项目写入结果。

### 5.2 修改与执行分离

编辑表单不等于运行。运行设置弹窗先保存修改草稿，“检查并应用”只把配置写入当前任务；“开始训练”或“发送／生成”才提交执行。配置变更不得隐式购买资源、下载新组件或替换正在运行的模型。

### 5.3 有效参数不能只停留在表单

服务端校验并返回 `effective_config`（实际执行配置）。如果用户请求的设置不被引擎支持，应拒绝或显式请求用户选择替代方案，不得默默忽略。引擎自动值必须被解析或明确标为“由引擎动态决定”。

### 5.4 失败是可保留结果

任务失败要保存输入、配置、环境、日志、错误分类和最近可用检查点。重试默认新建尝试并关联旧任务；恢复检查点则明确展示从哪个步骤继续。失败候选可以保留为研究记录，但不能通过“登记可用候选”入口混入正常模型库。

### 5.5 评测和发布分别决定

训练完成只表示执行结束，评测通过只表示指定评测范围达标，登记候选只表示可进入后续试用。导出成功、目标设备加载通过、发布完成是另外三种状态，各自需要证据。

### 5.6 可见选择与实际执行一致

模型、任务模式、输入素材、产物格式、引擎、设备和优化组件必须一起校验。改变上游选择时，先在草稿中标明失效项与替代值，再由用户应用；不能保留界面已经不可见的旧选项继续提交。准备状态绑定精确组件与环境版本，不能跨策略继承一个“已准备”布尔值。执行位置、数据发送目的地、运行摘要与提交快照必须来自同一份已应用配置。

### 5.7 需求修订与实现状态分开

本轮 14 项审计问题已进入专项规范、工作包和验收；5 项增强建议按限定范围进入计划。文档处理完成不改变现有 Demo 的实现状态。逐项状态与需求追踪以 [16 审计整改与需求追踪](16-audit-remediation-plan.md) 为准。

## 6. 非功能目标

以下是建议验收目标，M0 用参考设备和代表性数据校准；当前没有性能实测结果。

| 类别 | 目标 | 验证方法 |
| --- | --- | --- |
| 可用性 | 首次用户可沿界面完成模型准备到首次结果；错误有位置和处理入口 | 5 名目标用户完成代表任务，记录阻塞点 |
| 交互响应 | 不含模型计算的常规本地操作 p95 不超过 300 ms | 参考机器记录交互时间，长操作异步化 |
| 初次可见 | 已安装环境、常规数据规模下主窗口冷启动目标不超过 3 秒 | 20 次独立启动；不计首次模型下载 |
| 数据规模 | 首轮覆盖 1 万任务索引、100 万条数据元信息；列表分页读取 | 生成测试数据，检查内存与查询耗时 |
| 稳定性 | 运行器退出不导致前端丢失草稿；重复提交不重复执行 | 故障注入和幂等测试 |
| 可追溯 | 完成任务必须具有模型版本、数据版本或输入摘要、环境、配方、产物清单 | 全量结构校验 |
| 可访问性 | 关键任务可通过键盘完成；标签、焦点、错误关联明确 | 自动检查加手工键盘路径 |
| 外观适配 | 深浅色；桌面 1024 px、中等 736 px、窄屏 360 px；最小 320 px 不横向溢出 | 浏览器／应用真实检查 |
| 离线能力 | 已准备资源的本地推理不强制联网；缺失资源说明清楚 | 断网运行与缓存命中测试 |
| 性能诚实性 | 不展示未实测的 tokens/s、显存占用、ANE 使用率或加速倍数 | 指标来源检查，缺失值显示未测 |

## 7. 成功指标与质量度量

产品内测先度量可完成性：核心路径完成率、首次结果耗时、任务恢复成功率、错误修正次数、配方复用成功率。业务侧再度量模型质量和资源成本，不用下载数量或训练次数替代成功率。

指标必须包含样本数、测试条件和排除项。例如首次结果耗时分别记录环境准备、下载、模型加载、Prefill 和 Decode；训练耗时分别记录预处理、加载、优化步骤、检查点写入与评测。不同硬件之间不得以不相同输入或量化方式直接排名。

## 8. 第一版真实闭环的放行定义

首个内测版本至少在一个明确的 Apple 本地推理组合和一个明确的 NVIDIA 训练组合上完成：真实导入数据、真实模型加载、SFT + LoRA 小样本训练、独立评测、登记候选、候选试用、配方保存、应用重启后恢复。其他类别和硬件继续保留产品结构，但其状态必须与验收矩阵一致。

M0 先用同一份最小 LoRA 实物完成跨端技术试验，核对基座、适配器模块、模板和目标引擎，不等待产品导出器。M3 再通过正式产品入口完成同一链路；不能以两端各跑一个无关模型代替。首次用户路径另设 AC-25，完整回程与导出分别对应 AC-26、AC-27。
