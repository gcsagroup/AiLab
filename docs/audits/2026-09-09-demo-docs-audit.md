## 1. 结论与处理范围

**产品结构可以保留，当前文档可以支持 M0 技术试验，但还不适合直接冻结为正式开发和验收合同。** 本轮确认 14 项问题：6 项 Demo 行为错误、5 项技术合同遗漏、3 项开发与验收问题。其中 4 项列为 P1，10 项列为 P2；另外提出 5 项增强建议。没有发现需要推翻四类工作台、模型库、数据市场或模型实验室的依据。

P1 表示应优先修正的流程完整性或阶段放行问题；P2 表示应在相关模块实施前补齐的问题。这里的等级服务于本次审计，不是对不存在的真实后端进行漏洞评级。

本轮只增加审计报告与独立复现脚本。未改原 Demo、原 17 份文档、构建脚本或原测试；未安装模型、驱动或后端，未部署服务。下列建议尚未实施，不能读作“问题已修复”。

## 3. Demo 行为问题

### AUD-01：同一工作流重新开始后，旧结果可以直接推进

**位置：**[最终 HTML 第 323 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-unified.html:323>)；配套 `ailab-unified-ui.js` 第 20、71、72 行。

**浏览器复现：**载入“商品图 → 视频 → 配音”，第一步生成香水图 GEN-41；退出工作流后重新载入，把提示词改成“红色茶壶，纯白背景”，没有生成新图就点击“带入下一步”。界面成功进入第 2 步，参考图仍显示“来自 GEN-41”。

独立反例进一步完成了两轮三步流程：第二轮新增生成任务数为 0，仍可保存完整工作流，输出编号与第一轮完全相同。工作流只保存定义编号，没有本次执行编号；结果选择为空时会退回历史第一项，下一步仅检查模型与工作流定义。

**影响：**用户以为新输入已经生效，实际后续步骤继续使用旧图。显式复用旧结果可以是功能，但当前没有这一步选择和来源确认。

**最小修改：**工作流执行、步骤尝试与输入版本分别编号；下一步默认接受当前执行当前步骤的产物。复用旧结果须有明确动作和记录。修改输入后展示旧结果的来源状态。

**验收：**完整执行两轮；第二轮未生成时不得直接成功；显式复用时记录来源；修改第一步后下游旧产物标记失效。

**与已知差距的关系：**14 已记录“旧输入失效／重做”待实现，但未具体披露新一轮可以零次生成就保存。此处是新增实证，不是重复报告预置图片 GAP-03。

### AUD-02：目标类别有任务时，步骤推进不是完整事务

**位置：**[最终 HTML 第 323 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-unified.html:323>)；配套 `ailab-unified-ui.js` 第 69、72 行。

**触发：**先生成并暂停一个视频任务，再载入商品工作流并完成图片，点击“带入下一步”。代码先加入输出并增加步骤，随后切换到视频页时才发现视频类别有任务，拒绝切换。后续代码仍继续修改当前草稿。

**反例结果：**工作流处于第 2 步，但当前类别仍为图片；图片草稿的来源被设为自己刚生成的图片编号。界面提示类别有任务，却已经变更步骤，继续操作会卡在不一致状态。

**最小修改：**先完成目标类别可进入性检查，再一次性提交步骤、输出和新草稿引用。失败保留原步骤，并提供查看阻塞任务、等待或退出的明确动作。

**验收：**目标任务运行中、暂停中、刚好完成、刚好取消四种条件；失败时步骤、输出集合、源草稿均不变，解除阻塞后一次点击只推进一次。

### AUD-03：切换推测策略时没有清除不兼容草稿

**位置：**[运行状态逻辑第 18 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-runtime-state.js:18>)及第 21 行；对应最终 HTML 第 229、232 行。

**浏览器复现：**Qwen3-4B → 云 GPU／vLLM → 关闭思考 → 普通草稿 → 选择并模拟准备草稿 → 只切换策略为 DFlash。界面仍显示“演示组件已准备”，可以应用、发送并完成 GEN-42。

结果配方实际记录：

```json

```

当前 DFlash 选项对应 `qwen4-dflash`。准备是否真实并不是本问题的关键；现有静态配对关系本身已经不一致。

**最小修改：**策略改变时清除不匹配的草稿和准备状态；应用与提交均重新验证目标模型、策略、组件编号和引擎。准备状态应属于一个确定组合，不能是独立布尔开关。

**验收：**普通草稿与 DFlash 双向切换，准备前后切换模型／引擎，以及直接提交旧配置；所有不匹配组合均阻断。

**最小修改：**产物格式参与默认引擎选择和最终加载能力检查；候选继承来源信息时，不继承已经不适用的运行配置。需要桥接时将桥接步骤列为独立准备动作。

**验收：**转换产物从“候选 → 运行”入口真实经过完整选择链；正确格式和引擎通过，错误方向均阻断。不能仅测试“原始权重不能用 ANE”一个方向。

## 4. 技术合同遗漏

### AUD-07：暂停和取消中途出现异常时没有闭合处理

**位置：**[07 任务状态机](../07-api-and-task-lifecycle.md)第 129—144 行；控制接口第 44—47 行；取消说明第 174 行。

状态图中 `pausing` 只能进入 `paused`，没有写检查点失败或暂停时再次取消的出口；`cancelling` 只有执行器确认停止后的成功出口。正文提到强制终止入口，却未给相应命令、结果和状态合同。

对状态图进行代表性序列检查，确认未表达 `pausing→failed`、`pausing→cancelling`、`cancelling→failed`。实际设计可以选择回到运行、保留待确认状态等其他策略，关键是明确约定每个事件的结果；不是要求机械增加这三条边就算修复。

**最小修改：**补状态转移表与可用动作，覆盖暂停失败、暂停时取消、取消时崩溃、超时强制终止和停止结果未知。控制命令统一版本检查、幂等与错误反馈。

**验收：**逐事件表驱动检查，加取消／完成竞争、重复控制、断连补拉；没有执行器证据时不能显示已停止。

**已有覆盖：**07 已定义安全点、取消确认、连接状态与运行状态分离；11 已有一般故障测试。本问题是这些规则在异常分支上没有闭合，不能概括为“完全没有恢复设计”。

### AUD-08：产物补收与计算重试混在一起

**位置：**[12 运维](../12-operations-and-release.md)第 57、62 行；[07 接口](../07-api-and-task-lifecycle.md)第 47、137—143、178 行；[06 适配器](../06-architecture-and-adapters.md)第 92 行。

运维文档允许磁盘满后“重试收集”；执行器已有 `collect`。但状态合同将收集／登记失败归为执行失败终态，公开重试动作只会建立新的计算尝试草稿，没有仅补传文件、校验并登记的操作。

**影响：**训练已经完成、远端文件完整，仅本地写入失败时，团队没有明确实现路径来恢复成果而不重跑训练。

**最小修改：**分开计算结果和收集状态，或新增幂等补收操作并引用原产物清单。保留原尝试记录，不把补收成功伪装成重新计算。

**验收：**计算完成后磁盘满、传输中断、登记事务失败；恢复后计算调用次数不增加，文件摘要一致、资产登记一次。

### AUD-09：多模态前缀缓存缺媒体身份条件

**位置：**[04 缓存规范](../04-runtime-and-hardware.md)第 69 行。

最小缓存键列出模型、适配器、tokenizer、模板、token 前缀、精度和隔离范围，但没有媒体内容摘要、处理器和预处理参数。相同问题配不同图片时，媒体占位 token 可能相同。vLLM 官方专门用图片哈希区分此情况。[官方说明](https://docs.vllm.ai/en/latest/design/prefix_caching/)

**最小修改：**缓存身份纳入媒体内容或编码结果、媒体顺序、处理器版本及裁剪／抽帧等参数。若交由底层引擎管理，应要求适配器确认这些条件；不能另建弱化的应用层缓存。未知组合保持关闭。

**验收：**相同文字、不同图片／视频／音频不能错误命中；相同媒体改变裁剪、顺序或处理器版本后正确失效。

**边界：**项目尚无真实缓存实现，本项是会影响正确性的设计遗漏；04 已有媒体 token 预算和项目隔离规范。

### AUD-10：SFT 数据通过结构检查，不代表监督目标已确定

**位置：**[03 训练参数](../03-training-and-model-lab.md)第 53 行；[05 数据样例与检查](../05-data-model-and-assets.md)第 65、136、160 行。

文档保存了 messages、模板与 tokenizer 版本，但没有固定哪些 token 参与损失计算、EOS／PAD、截断方向、样本拼接和边界策略。不同适配器可能对同一数据训练不同目标；超长样本可能留下问题却丢掉回答。

TRL 将 assistant-only、completion-only 与 packing 分别定义，并对聊天模板提出具体要求。[官方说明](https://huggingface.co/docs/trl/sft_trainer)

**最小修改：**增加版本化的分词和监督配方；可用训练模板固定策略，不必把每项都变成普通用户要填写的参数。展示有效监督 token、截断和丢弃样本统计。

**验收：**多轮对话、超长回答、空回答、只有系统消息、padding、拼接边界与多模态样本；核对最终 token 与 labels，零有效监督样本拒绝训练。

### AUD-11：模型格式的执行风险没有进入导入合同

**位置：**[06 环境与信任边界](../06-architecture-and-adapters.md)第 127、131 行；[07 模型导入计划](../07-api-and-task-lifecycle.md)第 25 行；[05 模型版本](../05-data-model-and-assets.md)第 160 行。

文档已将自定义仓库代码执行作为独立信任决定，但没有覆盖第三方 pickle、TorchScript 和检查点加载方式。哈希正确且没有运行仓库脚本，不代表加载模型文件没有执行风险。PyTorch 明确要求把未知 TorchScript 按可执行代码处理，并区分序列化格式的风险。[官方政策](https://github.com/pytorch/pytorch/security/policy)

**最小修改：**导入计划记录加载方式与信任类别；常规权重采用允许格式和受限加载，失败时不得自动降级为任意反序列化。需要执行代码的格式单独决定，并限制可访问文件、网络和凭证。

**验收：**受限加载失败、格式伪装、不受信任检查点、需要自定义代码的模型；验证拒绝、明确提示和隔离。依赖环境隔离不能替代执行权限隔离。

**边界：**这是设计合同审计，没有尝试执行恶意模型，也没有证明当前应用存在真实代码执行漏洞。

### AUD-12：M0 技术试验绑定了后期产品验收

**位置：**[10 工作包](../10-work-breakdown.md)第 17—20、59—61、99 行；[11 验收](../11-testing-and-acceptance.md)第 48、92、132 行。

WP-02 属于 M0，交付桌面壳与侧进程试验，却要求 AC-01 和 AC-22。AC-01 包括双项目数据库草稿／历史重启恢复，主要存储到 M1 才建；AC-22 包括候选安装包、升级、迁移回滚、备份恢复和导出，相关工作包在 M6。WP-04 又依赖 WP-02，工作包完成标准要求相关测试齐全。

**影响：**按照任务卡执行，M0 没有独立可判定的退出门槛。团队可能提前勾选最终验收，也可能因等待后期工作而无法推进。WP-01 对完整硬件 AC-12 的引用也需要分阶段解释。

**最小修改：**为 M0 建立技术试验验收，或将 AC 明确拆成阶段子项，区分“本阶段试验通过”和“完整产品验收通过”。最终验收保留在对应交付阶段汇总。

**验收：**每个 M0 工作包可以只依赖当阶段交付物完成；依赖图无阶段倒挂，验收子项都有明确执行条件。

### AUD-13：普通产物导出没有明确负责人和交付物

需求要求模型、适配器、作品和报告导出，对照表指向 WP-24／29。但前者交付转换与 ANE，后者交付安装更新和诊断导出，均未明确承担用户产物导出器。诊断包不能替代用户模型和作品导出。

**最小修改：**在现有工作包中明确负责人、阶段和导出器范围：选对象、解析依赖、清单、打包落盘、完整性、失败恢复及独立环境使用。没有必要为了编号再新建一个大模块。

**验收：**四类导出对象各有样例；适配器包含基座依赖；媒体可独立打开；评测报告可追踪；缺文件或取消时不产出伪完整包。

## 6. 建议增强的五个方向

这些建议尚未列入已确认缺陷数量；应按成本和产品目标取舍，不应因此无限扩张首期范围。

| 建议 | 解决的问题 | 最小落地方式 | 可验证结果 |
| --- | --- | --- | --- |
| E-01 首次使用完整路径与续做入口 | 首页偏训练；首次运行和最近生成任务不够直接，现有 AC 未完整覆盖零资源到首次结果 | 保留四类入口，增加类别内直接试用／继续上次运行；单列首次用户用例 | 5 名目标用户从干净环境完成准备模型、检查设备、首次结果，无需读开发文档，记录阻塞和耗时 |
| E-02 常用运行预设与配置差异 | 参数已足够多，普通用户难判断哪些值得改 | 提供“模型默认、低内存、低延迟”少量可验证模板；保留完整高级设置；应用前显示实际字段变化 | 取消不变；换设备后能解释哪些值失效、哪些需重载；不虚构性能收益 |
| E-03 把训练产物回到目标设备的验证前移 | NVIDIA 训练与 Apple 试用可能在产物格式、模块和引擎上断开 | M0 用同一份实际 LoRA 产物验证指定试用路径；需要转换就明确步骤 | 基座 revision、适配器、模板、目标引擎和试用结果形成一条证据链 |
| E-04 编辑结果与生成配方分开 | 字幕编辑会写入结果配方，但弹窗仍称其来自提交时固定设置 | 保存原输出；字幕校正作为结果版本或后处理记录，分别展示生成参数和编辑内容 | 可查看原转写与修订差异；复跑生成不隐含复用人工校正；任务快照保持不可变 |
| E-05 将审计基线变成团队可复跑资产 | Demo、源码、测试目前在个人会话目录，文档链接依赖本机绝对路径 | 后续经项目组织决策，将确认的原型及检查器纳入项目固定位置并保存清单和摘要 | 新成员从同一版本取到 Demo、测试和文档，一条明确命令复跑；保留旧资产，不以迁移名义删除 |

E-04 已观察到 `result.recipe.transcript` 随字幕编辑改变，而 `job.snapshot` 没有变化。这里要明确的是配方语义与展示，不是报告“执行快照可被篡改”。
