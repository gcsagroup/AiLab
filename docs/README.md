## 1. 文档用途与当前结论

这套文档用于把已经确定的产品原型转成可实施、可分工、可验收的开发基线。覆盖产品范围、交互流程、训练与推理、硬件适配、数据与资产、技术架构、接口、AI 辅助、开发排期、测试和发布。

**当前交付是审计修订后的设计与开发计划，Demo 修复与真实产品实现仍待执行。** 1.1 已补工作流身份、参数联动、异常控制、产物补收、媒体缓存、SFT 监督、模型加载信任和导出合同；阶段验证与最终验收分开。当前可开展有边界的 M0 技术试验，具体模型、设备、人员和日期仍需依据实测锁定。

原型的 42 组主流程与 17 组运行优化测试仍只证明其覆盖的演示行为；审计发现的 6 项行为问题未因文档更新而消失。详细实施状态见 [16 审计整改与需求追踪](16-audit-remediation-plan.md)，当前验证证据见 [验证报告](validation-report.md)。

本套文档使用以下状态，后续评审和开发不得混用：

| 状态 | 含义 | 能否对外称为支持 |
| --- | --- | --- |
| 原型已表现 | Demo 存在对应页面、配置或模拟流程 | 只能称为原型功能 |
| 规范待实现 | 本文明确要求、真实应用尚未实现 | 不能 |
| 技术方案建议 | 为开发提出的选型或结构，可由技术验证调整 | 不能 |
| 待验证组合 | 上游存在相关能力，但本项目未验证完整组合 | 不能 |
| 实机验收通过 | 精确设备、模型、版本、参数与报告均有证据 | 仅能声明报告覆盖的范围 |
| 文档处理完成 | 规范、责任与验收已更新，实现状态单独记录 | 不能据此宣称功能已修复 |

## 3. 产品不变的骨架

1. 工作台按语言与多模态、图片、视频、音频四类模型组织任务。
2. 每类提供训练／微调、运行／试用、任务与结果，保留在同一类别内继续工作的路径。
3. 模型库、工作流、数据集市场、模型实验室、作品与素材、设备环境继续保留。
4. 训练类型与参数更新方式分开表达，例如 SFT + LoRA。
5. 运行配置必须体现模型、引擎、设备和版本的组合能力。
6. AI 只提出建议，修改、执行、登记和对外操作由用户决定。
7. 来源记录、提供方访问控制和用户声明分别保存，AI 不代判数据授权或合法性。

## 4. 文档之间如何保持一致

- 功能需求编号统一使用 `PRD-xxx`，在 01 定义；工作包编号使用 `WP-xx`，在 10 定义；验收用例编号使用 `AC-xx`，在 11 定义。
- 运行参数语义以 04 为准；训练语义以 03 为准；对象与版本关系以 05 为准；任务状态以 07 为准。
- 真实产品行为与 Demo 不同时，在 14 记录差距，并在 10 分配修复工作包，不把演示中的简化实现直接复制成产品规范。
- 阶段划分统一为 M0—M6，阶段定义以 09 为准。估算是资源假设下的计划，不是已承诺的发布日期。
- M0 使用 TV-01—TV-03；M1—M6 使用明确的阶段门槛。工作包的最终 AC 只是完整验收追踪，不把后期验收当作早期试验的前置条件。
- 需求定义、工作包责任和 AC 直接覆盖关系与 16 双向一致；结构检查和人工内容复核分别记录，不把编号出现过视为语义一致。
- 需要新增顶级入口或改变 AI 操作边界时，先更新产品需求与交互，再更新实现任务。
- 模型名称、引擎版本、精度支持和性能结论会变化，必须通过能力记录和实测报告更新，不依赖文档中一个固定的“支持”勾选。
