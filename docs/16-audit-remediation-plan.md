## 5. 实施顺序和关闭条件

| 顺序 | 要做的工作 | 通过后可以做什么 | 仍不能宣称什么 |
| --- | --- | --- | --- |
| 本轮文档修订 | 专项合同、阶段依赖、责任和直接需求追踪；文档工具正负例 | 使用 1.1 规范开展有边界的技术试验 | Demo 问题已修、产品开发已完成 |
| M0 | TV-01 组合、TV-02 壳侧进程、TV-03 同一 LoRA 回程；重估新增工作量 | 锁定首期组合及下一阶段任务卡 | M3 训练产品或 M6 发布验收通过 |
| M1—M2 | 工作流对象基础、状态／补收合同、模型信任、参数联动与统一执行位置 | 进入指定组合真实推理和恢复验收 | 未接入媒体或推测策略已支持 |
| M3 | 监督配方、检查点、候选回程、模型／适配器／文本作品／报告导出 | 形成限定范围私有 Alpha | 所有方法和所有设备都能训练 |
| M4—M5 | 工作流原子推进、媒体编辑／导出、转换和推测组合 | 对已验证扩展逐项开放 | 仅控件可见就算硬件或优化通过 |
| M6 | 同一候选包全流程、首次用户、升级／恢复和最终 AC | 按冻结范围做发布准备 | 未执行外部发布已经完成 |

P1 的流程与状态规则先进入合同与回归设计；具体 UI 修复随相应产品工作包完成，已知问题在此之前保留。不要求为了修 Demo 的计时器先做一套与正式产品并行维护的临时后端。

单项实现关闭需要：具体修改版本、相关模型／数据／环境身份、预期行为回归、代表性负例、产物或日志证据、负责人和验收日期。纯文档项可在关系检查与内容复核后关闭文档状态；需要运行证据的项仍保留待实现／待测。

## 6. 文档维护与验证

20 项需求、30 个顶层工作包、27 项最终 AC、3 项 M0 技术试验、14 项问题及 5 项增强分别以本套文件的定义和追踪表为准。顶层文档数量不是质量门槛；历史归档与审计材料不参与当前需求编号约束。

文档检查覆盖链接、表格、代码块、JSON、编号和范围、直接覆盖关系、实际阶段数字、依赖及整改状态；仍需要人工判断规范是否可实现、测试是否足够。负例故意破坏映射、周期、阶段和链接，验证工具能明确报错；不会修改当前文档。

本轮结果见 [验证报告](validation-report.md)。后续如果改变产物格式、模型版本、阶段或责任，应同时更新专项、10、11、本页与受影响测试。原审计保留为历史证据，不把原来“问题存在”的断言通过当作修复验收通过。
