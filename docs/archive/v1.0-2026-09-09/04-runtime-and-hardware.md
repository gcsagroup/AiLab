# 运行参数、优化与硬件适配规格

版本：1.0 · 日期：2026-09-09 · 状态：以最终运行优化 Demo 为需求基线；真实后端待接入。

相关文档：[接口合同](07-api-and-task-lifecycle.md)、[架构](06-architecture-and-adapters.md)、[性能验收](11-testing-and-acceptance.md)。

## 1. 核心原则

运行能力由“模型版本 × 模型格式 × tokenizer／处理器 × 引擎版本 × 操作系统 × 驱动 × 硬件 × 参数组合”共同决定。品牌名、文件下载完成或设备连接成功都不足以确定支持。

产品必须同时保存用户请求配置、校验结果、引擎实际执行配置和运行证据。所有字段都有适用条件、单位和作用阶段。不能用一个大 JSON 输入框代替完整的配置界面，也不能把不同引擎名称相似的参数无条件互相映射。

## 2. 参数层级与生效时机

| 层级 | 示例 | 修改后的动作 | 与已有任务的关系 |
| --- | --- | --- | --- |
| 单次请求 | temperature、最大输出、停止词、思考模式 | 下次请求生效 | 不修改执行中请求 |
| 会话／输入管理 | 上下文限额、历史裁剪、缓存隔离 | 重新计算输入和缓存键 | 不改变已经保存的结果 |
| 引擎实例 | KV dtype、批处理预算、CUDA Graph | 可能需要重新加载或重启实例 | 先排空或新建实例，不能静默打断任务 |
| 模型加载 | 权重精度、适配器、GPU 卸载、并行布局 | 加载新实例并检查 | 保留旧实例上的任务归属 |
| 部署 | Prefill／Decode 分离、远程连接器 | 单独部署与验收 | 不通过请求表单隐式部署 |

界面在应用前展示哪些修改需要重启、重新加载或重新分词。默认值取自版本化模型模板；真实执行时应显示已解析后的数值或明确的自动策略。

## 3. 生成与上下文字段

本节“Demo 默认”只描述当前原型。正式默认值从能力声明与模型推荐配置生成。

| 字段 | 中文含义 | Demo 默认 | 正式校验与语义 |
| --- | --- | --- | --- |
| `thinking` | 思考模式 | `default` | 默认／关闭／开启；只有模型和模板明确支持时可切换 |
| `context` | 上下文限制 | 8192 token | 输入、历史、系统指令、媒体 token、输出合计受限 |
| `maxOutput` | 最大输出 | 1024 token | 必须给输入留空间；最终根据实际分词结果检查 |
| `overflow` | 超限处理 | `reject` | 拒绝或裁剪最旧对话；保留系统消息与工具调用完整性 |
| `temperature` | 温度 | 0.7 | 有限非负数；0 的含义由引擎映射为确定性策略并记录 |
| `topP` | 累积概率采样 | 0.9 | 有效范围由引擎定义，空值不能变成 0 |
| `topK` | 候选数量 | 20 | 0 表示不限制只在适配器确实如此解释时使用 |
| `minP` | 最小相对概率 | 0 | 不支持该采样器时不得悄悄忽略 |
| `repeatPenalty` | 重复惩罚 | 1.05 | 与 presence／frequency penalty 区分，不能直接替代 |
| `stop` | 停止序列 | 空 | 正式产品使用字符串数组；界面按行输入后解析 |
| `stream` | 流式输出 | 开启 | 区分服务端流、前端展示和最终结果持久化 |
| 任务 `seed` | 随机种子 | 42 | 随结果保存；跨引擎相同种子不承诺逐字相同 |

### 3.1 关闭思考

以 [Qwen3-4B 模型说明](https://huggingface.co/Qwen/Qwen3-4B)中的模板控制为参考实现一个明确组合。实际适配必须确认思考开关如何传到模板和推理接口，不能只在输出后移除思考文本。

模型只有一种行为模式、模板不接受开关或远程服务不支持时，界面显示模型默认并解释原因。输出显示策略与模型思考计算分开记录。思考预算是后续按引擎声明开放的参数，当前 Demo 没有单独实现其预算控制，不以 `maxOutput` 冒充完整的思考预算。

### 3.2 上下文预算

提交前使用本次模型的 tokenizer／处理器计算实际输入 token。多模态输入必须计入模型处理后的媒体 token，不能只统计问题字符数。预留系统消息、模板标记和输出空间，超过限额时执行用户选择的策略。

Demo 的 512—32,768 校验范围是演示约束，不是所有 Qwen 模型或所有引擎的产品上限。正式最大值来自模型能力、引擎配置和资源约束；上下文扩展方法需要独立版本与质量验证。

## 4. KV Cache 与前缀缓存

| 字段 | 含义 | Demo 默认 | 正式要求 |
| --- | --- | --- | --- |
| `kvPrecision` | KV 存储精度 | auto | 分引擎列出 dtype／量化格式；和权重量化独立 |
| `kvBudget` | KV token 容量／窗口 | 8192 | 必须标注它在该引擎中是容量、窗口还是由预算推导的估计值 |
| `prefixCache` | 提示词／前缀复用 | 关闭 | 仅在引擎确实支持并可验证命中时启用 |
| `cacheScope` | 缓存隔离 | 当前任务 | 可选择项目范围；不跨项目共享私有输入 |

当前原型提供 MLX 的 auto／8-bit／4-bit、llama.cpp 的 auto／f16／q8_0／q4_0、服务引擎的 auto／fp8 示例。真实适配必须验证版本与设备的格式组合，不能把这些列表直接认定为完整可用列表。

KV 容量的统一界面语义要谨慎处理：MLX 的旋转缓存窗口会丢弃更早 KV；服务引擎通常通过显存预算、块管理或具体 cache 配置管理容量。适配器必须输出实际映射，无法等价映射时更换字段标签并显示原因。

缓存键至少包括模型版本、权重／适配器组合、tokenizer、聊天模板、输入 token 前缀、KV 精度和隔离范围。模型／模板／适配器改变后失效。缓存数据不能进入普通诊断包；清理缓存不能删除用户模型和作品。

## 5. Prefill 与 Decode 调度

| 字段 | 含义 | Demo 默认 | 适用与验收 |
| --- | --- | --- | --- |
| `prefillChunk` | 输入处理分块大小 | 512 token | 单请求步长与服务端 chunked prefill 区分 |
| `chunkedPrefill` | 服务端分块调度 | 关闭 | 按 vLLM／SGLang 具体版本和架构适配 |
| `batchTokens` | 批处理 token 预算 | 2048 | 检查与分块、最大序列及调度规则的关系 |
| `decodeBatch` | 并发序列数 | 1 | 本次实例并发上限；不等于训练批量 |
| `attention` | Attention 实现 | auto | 由模型算子、引擎和设备共同决定 |
| `graphs` | CUDA Graph | 关闭 | 需要合适的形状、预热、显存和引擎支持 |
| `splitPD` | Prefill／Decode 分离 | 关闭 | 属于部署能力，需要连接器和故障恢复 |
| `prefillEndpoint` | Prefill 服务地址 | 空 | 验证服务身份、模型版本、可用性 |
| `decodeEndpoint` | Decode 服务地址 | 空 | 需与 Prefill 的 KV 格式和传输协议兼容 |

参考 [vLLM 调优说明](https://docs.vllm.ai/en/latest/configuration/optimization/)定义测试条件，但不将上游默认值写死为产品默认。较大批处理通常服务于吞吐，较小输入分块可能影响首 token 和调度公平性，必须以实测决定。

前后端分离部署在 Demo 中没有真实服务或 KV 传输连接器，当前应保持阻断。正式实现需要额外验证远端身份、传输失败、模型版本错配、缓存传输超时和请求恢复，不能靠两个 URL 输入框就称为支持。

## 6. 推测解码

| 策略 | 必要依赖 | 配置 | 验证重点 |
| --- | --- | --- | --- |
| 关闭 | 正常目标模型 | 无草稿组件 | 正常基线 |
| 普通草稿模型 | 目标、草稿、tokenizer／词表兼容、引擎适配 | 草稿版本、精度、推测长度 | 分布／正确性、接受率、总延迟 |
| MTP | 目标模型原生预测能力或对应配套组件、引擎实现 | 预测组件、推测长度、验证模式 | 组件匹配、逐步验证与回归 |
| DFlash | 目标模型、匹配的块扩散草稿、引擎与版本 | 草稿配对、块大小、草稿精度 | 家族／思考模式条件、接受率、验证成本 |

Demo 字段为 `speculation`、`draftModel`、`draftReady`、`specTokens`、`draftPrecision`。其中 `draftReady` 当前只是模拟状态，真实实现必须拆成下载完整、哈希校验、加载、配对验证四个阶段。

[vLLM MTP 文档](https://docs.vllm.ai/en/latest/features/speculative_decoding/mtp/)将 MTP 作为依赖模型能力的路径；当前 Demo 中的 Qwen3-4B 不应因用户勾选 MTP 就获得原生预测组件。

[DFlash 官方项目](https://github.com/z-lab/dflash)列出了特定模型与本地／服务后端路径。不能泛称 DFlash 只支持 CUDA，也不能泛称任意 MLX 模型都可开启。当前 Demo 使用 Qwen3-4B 非思考模式配套示例；正式实现锁定目标 revision、草稿 revision、引擎 revision 和思考策略后再验收。

推测解码默认只选择一种策略。启用后不保证更快；必须测量草稿开销、接受率、Prefill、Decode、总延迟、吞吐和峰值内存。对不兼容配对拒绝执行，不能降级到标准生成后仍显示推测加速已开启。

## 7. 通用硬件与加载字段

| 字段 | 含义 | Demo 默认 | 正式规则 |
| --- | --- | --- | --- |
| `device` | 执行位置 | 全局默认设备 | 固定设备标识，不能只记录易变显示名 |
| `accelerator` | 硬件后端 | 按设备模板 | 验证厂商、架构、操作系统和驱动 |
| `engine` | 运行引擎 | 按模型类别与后端 | 记录实际二进制／包版本 |
| `precision` | 权重计算精度 | auto | FP16／BF16／FP32 只是候选，设备不支持时拒绝 |
| `memoryLimit` | 内存使用预算 | 80% | GPU 显存、统一内存和系统内存必须分开解释 |
| `cpuThreads` | CPU 线程 | 8 | 区分计算线程和输入处理线程 |
| `gpuLayers` | llama.cpp GPU 卸载层 | auto | 记录实际卸载结果，不能把请求 all 等同于全部成功 |
| `tensorParallel` | 张量并行设备数 | 1 | 校验设备数量、拓扑、模型切分与引擎支持 |
| `computeUnits` | Core ML 计算单元策略 | 按后端 | CPU_ONLY／CPU_AND_GPU／CPU_AND_NE／ALL 等策略 |

全局设备列表保留本机、自有服务器、云实例、AMD 工作站、Intel 工作站和 CPU 示例。真实设备条目必须通过探测数据生成，不能把 Demo 内的“Apple”“Linux”当成本机或用户服务器的真实硬件事实。

## 8. 硬件适配目标矩阵

所有条目当前均为**待验证的目标路径**。首期重点组合是 Apple 本地推理与 NVIDIA Linux 训练／推理，其余逐阶段加入。

| 硬件／软件栈 | 候选引擎 | 运行目标 | 训练目标 | 关键限制与检查 |
| --- | --- | --- | --- | --- |
| Apple GPU／Metal | MLX-LM、MLX-VLM、llama.cpp | 文本及适配的多模态 | MLX 支持的模型方法 | 统一内存、模型转换、处理器和算子支持 |
| Apple GPU／MPS | PyTorch、Transformers、Diffusers | 媒体与适配模型 | 逐模型验证 | 不等同 CUDA；缺算子和回退需显式记录 |
| Apple ANE／Core ML | Core ML | 转换后的端侧模型 | 不作为通用训练后端 | 图划分、模型格式、静态／动态形状与设备执行 |
| NVIDIA／CUDA | PyTorch、vLLM、SGLang、llama.cpp、Diffusers | 文本、多模态、媒体 | PEFT／TRL 等已验证方法 | GPU 架构、驱动、CUDA、显存和精度 |
| AMD／ROCm／HIP | PyTorch、vLLM、SGLang、llama.cpp | 适配模型 | 逐方法验证 | 精确 GPU、系统、驱动及库版本 |
| Intel GPU／oneAPI／SYCL | llama.cpp 等已适配引擎 | GGUF 等适配模型 | 另行评估，不由推理能力推导 | 编译后端、Level Zero／SYCL 运行库和设备代际 |
| Intel／OpenVINO | OpenVINO | 支持插件上的 IR／可转换模型 | 不作为首期通用训练后端 | CPU／GPU／NPU 插件、模型格式和算子 |
| Vulkan GPU | llama.cpp 等 | 构建支持的模型 | 不作为首期训练后端 | 驱动、扩展和实际图形设备 |
| CPU | llama.cpp、PyTorch 等 | 小模型和回归基线 | 小规模功能性测试 | 内存、指令集、线程；不承诺大模型可用速度 |

官方边界参考：[Core ML 图执行](https://apple.github.io/coremltools/docs-guides/source/typed-execution.html)、[ROCm 兼容矩阵](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html)、[OpenVINO 设备模式](https://docs.openvino.ai/2025/openvino-workflow/running-inference/inference-devices-and-modes.html)、[llama.cpp](https://github.com/ggml-org/llama.cpp)。

### 8.1 ANE 的产品表达

ANE 是计算硬件，Core ML 是选择该路径的一种运行接口；MLX 使用 Apple GPU 的路径与它分开。选择 CPU + ANE 表示允许相应计算单元参与，不保证全部算子落到 ANE。正式报告应保存 Core ML 计算计划或可获得的执行证据；无法直接归因时标为“未确认实际 ANE 分配”。

### 8.2 训练与运行能力分别判断

设备可运行 GGUF 不等于能用该文件训练；ROCm 能加载模型不等于支持所选 QLoRA 实现；Intel GPU 的 SYCL 推理不等于提供对应训练后端。当前 Demo 训练端仍有简化判断，必须在真实实现中替换为统一能力查询。

## 9. 媒体模型参数

| 字段 | 用途 | Demo 默认 | 验收要求 |
| --- | --- | --- | --- |
| `scheduler` | 图像／视频采样调度器 | 模型默认 | 调度器与 checkpoint 配置匹配 |
| `sampling` | 采样步数 | 20 | 结果配方和真实 pipeline 参数一致 |
| `cfg` | 引导强度 | 7 | 只对使用该语义的模型开放 |
| `vaeTiling` | VAE 分块解码 | 关闭 | 检查拼接边界、内存和质量 |
| `vaeSlicing` | VAE 分批解码 | 关闭 | 检查批量维度和支持条件 |
| `offload` | CPU 卸载策略 | 无 | 区分按组件／顺序卸载，检查传输开销 |
| `compile` | 编译优化 | 关闭 | 区分首次编译与预热后性能，记录缓存 |
| `frames`／`fps` | 生成帧数／帧率 | 81／16 | 与时长、容器、模型限制一致 |
| `sampleRate` | 输出采样率 | 24000 Hz | 引擎原生采样率与后处理重采样分开 |
| `audioChunk` | 音频块时长 | 200 ms | 仅流式适配器支持时开放 |
| `streamAudio` | 分块音频输出 | 关闭 | 实际收到可播放块、顺序和最终文件完整 |
| `speed` | 语速 | 1.0 | 模型控制与后处理变速分别记录 |

参考 [Diffusers 内存优化](https://huggingface.co/docs/diffusers/optimization/memory)建立有条件的配置，不将 VAE、CFG、Euler 或 DPM++ 当成所有图片模型的通用能力。自定义图像融合网络可以完全不使用这些参数。

Demo 中视频时长、帧数与帧率仍是演示配置，实际产品必须在提交前统一换算并检查矛盾，不能同时保存多个互相冲突的“最终时长”。

## 10. 能力状态与诊断

能力至少具有未知、需准备、支持、条件支持、不支持、已验证六种状态。界面显示状态的依据与时间：文件、探测、配置检查或实机报告。

推荐诊断顺序：设备可达 → 硬件探测 → 驱动与运行库 → 引擎版本 → 模型文件／格式 → 加载 → 固定样例推理 → 目标优化验证。每一步单独保存结果，避免“连接成功”掩盖后续失败。

## 11. 参数验收合同

每个正式开放参数必须完成：字段类型校验、适用条件校验、后端参数映射、实际值回读、有效行为验证、配方保存、配方重载、错误提示。性能开关增加开／关对照与回归报告。

请求未被执行器采用时必须拒绝或返回明确的变更确认，不能把“界面保存成功”当作“优化已生效”。完整用例见 [11](11-testing-and-acceptance.md)。
