## 1. 工作包使用规则

每个工作包必须有具体责任人、输入版本、交付分支、测试记录和评审结果。下表的责任是角色建议，不代表已经安排人员。规模使用 S／M／L：S 约 2—4 人日，M 约 5—8 人日，L 约 9—15 人日；硬件或算法验证可能超出，应在技术试验后拆分。

这些规模只用于比较任务体量，不能把所有行直接相加当作项目承诺。适配器工作包可能按模型、设备和版本重复展开。

## 6. 重点工作包的可执行拆分

### WP-07 能力查询

1. 定义参数 schema：类型、单位、默认来源、允许值、冲突、重启要求。
2. 定义设备事实与版本摘要，支持探测失败／未知值。
3. 为首期两个引擎实现能力映射。
4. 前端根据 schema 生成可用选项，保留中文说明。
5. 提交端独立执行同样约束，返回实际参数。
6. 编写不支持组合与静默丢参测试。

完成条件：至少一个控件随模型／引擎／设备变化而改变，后端能拒绝伪造请求，实际执行记录与表单一致。

### WP-12 训练闭环

1. 将真实 JSONL 解析为固定数据版本，生成检查报告。
2. 按来源组划分训练与验证，固定种子。
3. 将 SFT + LoRA 参数映射到指定训练库版本。
4. 将步骤、损失、检查点和故障写为持久事件。
5. 验证取消、失败、新尝试与检查点恢复。
6. 输出独立适配器文件，并从干净进程加载。

完成条件：优化步骤确实更新了目标参数，产物可加载，原始模型／数据哈希保持不变；不能以退出码 0 代替这些检查。

### WP-17 推测解码

按策略拆成三个子任务，每个单独选择目标模型和组件。先测标准解码基线，再测开启策略；固定模型、精度、输入长度、输出长度和并发。保存接受率、总延迟和质量对照；无收益也允许结论为不建议默认开启。

### WP-24 转换与 ANE

先确认输入格式和形状，建立数值对照样例；转换后独立加载，再在目标设备运行。Core ML 计算单元策略与实际运行分配分别保存。不能取得 ANE 分配证据时，报告只能说 Core ML 执行通过。

## 7. 每张开发任务卡必须包含

目标、需求编号、输入资料、具体实现范围、明确不处理的相邻事项、依赖、交付文件、错误情形、自动测试、真实操作步骤、性能／数据边界、完成证据、审查人。

任务状态采用待开始、进行中、待评审、待验收、完成、阻塞。只有测试和所需实机证据齐全才进入完成。功能被延期时保留需求和原因，不删除追踪编号。

## 8. 第一批可启动任务

先安排 WP-01 与 WP-02 的技术试验，再根据结果完成 WP-03、WP-06、WP-07 合同；WP-04 与 WP-05 可在合同稳定后交错推进。不要在任务、版本和能力模型未确定前同时接入全部模型库。

本轮没有创建开发分支、安装环境或运行真实训练。以上工作包是后续开工使用的完整任务基线。
