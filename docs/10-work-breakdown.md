## 1. 工作包使用规则

每个工作包必须有具体责任人、输入版本、交付分支、测试记录和评审结果。下表的责任是角色建议，不代表已经安排人员。规模沿用 1.0 的相对体量 S／M／L；原参考为 S 约 2—4 人日、M 约 5—8 人日、L 约 9—15 人日。1.1 新增的异常恢复、导出、跨端和负例成本尚待 M0 实测后重估，不能把原体量当成新增内容已经包含的承诺。

顶层保留 WP-01—WP-30。跨阶段工作按第 6 节子项独立安排；子项是原工作包拆分，不是新增顶层模块。阶段验证列给出当前阶段可执行的门槛；最终 AC 列只追踪完整产品验收，**不要求早期工作包提前完成最终 AC 的全部内容**。阶段任务卡必须列出 [11 的阶段门槛](11-testing-and-acceptance.md) 中与本行交付物对应的子集及执行条件。

每个工作包的完成证据只适用于已验证模型、设备、版本和功能范围。未开放组合标记未测或延期，不能借阶段子集将完整 AC 标记通过。下表所有规模均待重新估算，适配器仍需按实际组合展开。

## 7. 重点工作包的可执行拆分

### WP-06：状态控制与只补收

1. 从 [07](07-api-and-task-lifecycle.md) 的状态表逐行生成正常、失败、超时和竞争测试；暂停检查点失败、暂停中取消、取消中崩溃、finalizing 中取消均有出口。
2. 暂停／恢复／取消／强制停止采用状态版本和幂等键，重复事件只裁决一次；无停止证据保留 `stop_status=unknown`，不伪报资源已释放。
3. 计算结果与收集记录独立。补收引用原尝试产物清单，校验、传输和登记均幂等；不得调用 `run`／`resume`，不得改变原 RunAttempt 终态。
4. M1 使用假执行器和真实文件／数据库完成合同故障测试，M2／M3 接入真实适配器后重跑对应分支。

### WP-07：能力与配置一致

1. 定义参数类型、单位、默认来源、允许值、冲突、重启要求与组合版本。
2. 绑定模型、基座／适配器、策略组件、引擎、设备、格式、任务模式和输入媒体能力；准备状态属于确定组合。
3. 变更任一依赖时重算有效性，显示需要清除／重置的字段，取消不改已应用设置。
4. 前端和提交端各自校验；覆盖普通草稿与 DFlash 双向切换、Omni 音频到视觉模型、Core ML 格式到不支持引擎的伪造提交。
5. 通过适配器回读实际参数；默认配置只能初始化新草稿，执行摘要与按钮旁位置使用已应用快照。

完成条件：界面、应用配置、请求快照与后端实际值一致，未知组合不能准备或执行；M1 合同通过不等于 M5 所有策略已实机支持。

### WP-12：监督目标与训练闭环

1. 解析真实 JSONL 并固定数据版本，按来源分组划分训练／验证，固定种子。
2. 保存 tokenizer、processor、模板与监督配方版本，固定 assistant-only／completion-only、EOS／PAD、截断和 packing 边界策略。
3. 为多轮、超长、空回答、仅系统消息、padding、拼接与多模态输入核对最终 tokens／labels；统计有效监督 token、截断／丢弃，零监督样本拒绝进入数据划分，训练集或必需验证集过滤后无有效监督则阻断任务。
4. 将 SFT + LoRA 映射到指定训练库版本，记录真实优化步、损失、检查点和故障事件。
5. 验证取消、失败新尝试、检查点恢复和只补收；从干净进程加载独立适配器，再完成目标设备试用。

完成条件：目标参数确实更新、原始模型／数据摘要不变、实际产物可加载且证据链完整；退出码 0 或损失下降均不能单独替代这些检查。

### WP-17、WP-24：组合与产物适配

推测解码按普通草稿、MTP、DFlash 拆为策略子任务；固定目标、组件、模板、思考条件、精度与并发，比较标准基线。切换使错误配套准备失效，准备前后及提交时都复核。保存接受率、总延迟和质量，无收益允许结论为不建议默认开启。

量化／转换先验证输入格式和形状，建立数值对照；转换候选默认引擎依据实际格式选择，不能继承不适用来源配置。从候选入口独立加载，两个错误格式／引擎方向都阻断。Core ML 策略与实际分配分别保存，无 ANE 证据只能说 Core ML 执行通过。

### WP-21：每轮工作流和原子推进

为每次 WorkflowRun、步骤尝试和输入版本固定编号；默认只接受当前轮当前步骤当前输入的产物，复用旧结果要明确操作并记录来源。修改上游输入后旧下游产物标记失效。目标类别可进入性检查、步骤推进、输出引用和目标草稿写入放在同一裁决事务中；检查失败全部不变。

复测两轮完整流程、第二轮零次生成、修改上游、目标运行／暂停／刚完成／刚取消及双击推进；失败提供查看阻塞任务、等待或退出，解除阻塞后只推进一次。

### WP-29：用户导出与发布分工

后端负责对象选择计划、依赖解析、manifest、摘要、部分文件与登记事务；前端负责范围／大小／依赖提示、保存位置、进度、取消和恢复；平台负责目标路径、权限与 M6 安装更新。正式指派人员时每项只有一个责任人，协作角色不能替代负责人。

模型、适配器、作品、报告各有真实样例。适配器包含固定基座依赖及缺失提示；不默认捆入无权分发的基座。媒体可独立打开；报告引用模型、数据、规则、结果和版本；结果修订保留原生成配方。缺文件、磁盘满、取消和校验失败不能产出伪完整包，恢复只处理导出，不触发模型重算。诊断包和普通用户产物包是不同导出类型。

## 8. 每张开发任务卡必须包含

目标、PRD／AUD／E 对应关系、输入版本、实现范围、依赖子项、交付文件、阶段验证子集、最终 AC 追踪、错误情形、自动测试、真实操作步骤、性能／数据边界、完成证据和审查人。

任务状态采用待开始、进行中、待评审、待验收、完成、阻塞。只有本阶段约定测试和实机证据齐全才进入阶段完成；最终 AC 在完整适用范围执行后单独签署。功能延期时保留需求、组合和原因，不删除追踪编号。

WP-30 从各阶段维护文档关系检查与负测，M6 汇总用户验收。检查 PRD → 工作包 → AC 的具体行关系、缺交付对象、参考周期求和、依赖子项和阶段倒挂；审计资产固定清单／摘要／复跑命令，保留历史来源，不把“成功复现已知问题”当产品测试通过。
