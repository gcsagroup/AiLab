# First-batch integration contracts

This file defines the first development batch's integration agreements. The full semantics are governed by docs/05 and 07. Implementation deviations must be reported to the overall lead and synchronized with callers.

<a id="控制服务"></a>

## Control service

The Python package `ailab_control` is located in `services/control`. Development startup: `python -m ailab_control --data-dir DIR --port 0`. It binds to 127.0.0.1, generates a random session Bearer token, and writes JSON `{"port":12345,"token":"...","pid":123}` as the first stdout line after successful startup; all logs go to stderr. Optional `--token-file PATH` is for the local development bridge only, with file permissions 0600. Logs must not expose the token.

All business interfaces are under `/api/v1` and validate the Bearer token. The unauthenticated health check exposes only whether the service is alive, with no directories or token. The Tauri host uses a Rust HTTP proxy and does not return the token to the frontend. In development, Vite binds only to loopback, reads authentication from the token file, and proxies requests to the verified local control endpoint.

Frontend calls consistently return `Promise<T>`. Response objects use the resource's original JSON; collections use `{"items":[]}` and errors use `{"error":{"code":"...","message":"中文","details":{}}}`. Create and edit operations return the complete object; IDs are generated by the server.

Priority interfaces: GET/POST /projects; GET /models; POST /models/import-plans, /models/imports; GET /datasets; POST /datasets/import-plans, /datasets/imports; GET /devices; GET /capabilities; POST /tasks; GET /tasks?project_id=; PATCH /tasks/{id}/draft; POST /tasks/{id}/preflight; POST /tasks/{id}/attempts; GET /attempts/{id}; GET /attempts/{id}/events (pagination JSON or SSE with explicit parameters); POST /attempts/{id}/cancel; GET /works?project_id=. Extend other interfaces according to actual delivery; do not return fabricated success.

A draft contains at least: kind=text/image/video/audio, operation=generate/train, model_id, nullable dataset_id, input={prompt,...}, runtime={engine,device_id,max_tokens,temperature,top_p,seed,...}. The initial implementation enables only connected real capabilities; other categories retain their entry points and specific preparation instructions. Task creation takes project_id, kind, operation, and name; editing takes draft and expected_revision. Submission takes preflight_id, expected_revision, and the Idempotency-Key request header.

<a id="执行器"></a>

## Executor

An independent Python process runs with an input snapshot file and output directory: `python workers/mlx_worker.py --snapshot FILE --output-dir DIR`. stdout contains newline-delimited JSON events: phase, token, metric, completed, error. completed includes artifacts (path, sha256, media_type) and effective_config; engine logs go to stderr. A snapshot contains attempt_id, operation, model_path, input, and runtime, plus dataset_path for training. Workers do not modify the control database. SIGTERM requests cancellation; the controller confirms that execution has stopped only after waiting for real process exit.

The local MLX environment is configured with an explicit absolute Python path and is separate from the control-service environment. Run commands as argument arrays; shell concatenation is prohibited. Pre-submission checks block execution when an executor or model is missing.
