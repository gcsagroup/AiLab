# 開發路線、里程碑與資源計劃

版本：1.0 · 日期：2026-09-09 · 狀態：基於最終 Demo 的建議排期；尚未開工、沒有實際交付日期。

相關文檔：[工作包](10-work-breakdown.md)、[測試門檻](11-testing-and-acceptance.md)、[風險與決策](13-decisions-risks-and-questions.md)。

<a id="1-实施顺序"></a>

## 1. 實施順序

先打通真實任務與數據保存，再擴展模型和硬件；先證明一個完整組合，再增加優化開關。四類工作台和現有輔助入口保持不變，後端按階段接入。未接入功能顯示實際狀態，不把全部功能隱藏到一個無法評審的“未來版本”。

第一條真實路徑選擇語言模型推理及 SFT + LoRA 閉環。它覆蓋項目、模型、數據、設備、執行、評測、產物、試用、配方、恢復，能夠驗證共用架構。隨後擴展媒體、專項實驗與多硬件，避免各模塊各建一套任務系統。

<a id="2-资源假设"></a>

## 2. 資源假設

| 角色 | 建議投入 | 職責 |
| --- | --- | --- |
| 產品／交互 | 0.5 人 | 需求取捨、流程驗收、文案與可用性 |
| 前端／桌面 | 1 人 | 頁面、表單、桌面宿主、狀態恢復 |
| 後端／平台 | 1 人 | 控制服務、元數據、文件、任務與遠程執行 |
| ML 訓練／推理 | 2 人 | 訓練、推理、媒體、量化與適配驗證 |
| 測試／質量 | 0.5—1 人 | 自動化、真實設備、回歸、發佈證據 |

估算基於約 5—5.5 人的持續投入，以及可用的 Apple Silicon、NVIDIA Linux 服務器和後續 AMD／Intel 測試設備。不是一個人執行的時間估算。沒有設備、數據或適配器許可／版本驗證時，相關階段單獨延期，不用模擬結果代替交付。

<a id="3-阶段总览"></a>

## 3. 階段總覽

| 階段 | 建議週期 | 主要目標 | 進入條件 | 退出條件 |
| --- | --- | --- | --- | --- |
| M0 範圍與技術驗證 | 1—2 周 | 凍結首期組合、打包與執行器最小驗證 | 本套文檔可評審 | 選型記錄、模型與設備清單、最小實機報告 |
| M1 應用與數據基礎 | 2—3 周 | 原型產品化、項目／資產／任務持久化 | M0 合同與存儲方向確定 | 草稿恢復、導入、隊列與事件合同通過 |
| M2 真實推理與運行配置 | 3—4 周 | Apple 本地與 NVIDIA 服務推理、真實參數 | M1 基礎可用 | 真實輸出、參數回讀、配方重載和取消通過 |
| M3 訓練與評測閉環 | 3—4 周 | SFT + LoRA、檢查點、評測、候選試用 | M1 數據和任務；M2 試用 | 數據到候選完整實機鏈路 |
| M4 媒體與數據市場 | 4—6 周 | 圖像／視頻／音頻最小組合與工作流 | 共用任務、產物、評測穩定 | 四類至少一個真實組合，市場返迴路徑通過 |
| M5 專項實驗與高級適配 | 4—6 周 | 蒸餾等專項、多硬件、緩存調度／推測優化 | 有基線模型、評測集與設備 | 每項獨立報告，未達標組合關閉 |
| M6 發佈與穩定化 | 2—3 周 | 安裝、升級、恢復、性能、文檔和發佈包 | 目標功能矩陣明確 | 發佈驗收清單完整，演示路徑與生產隔離 |

順序累計約 19—28 周，不含設備採購、較大上游阻塞或需求變更。允許不相依的模塊有限交錯，但必須保留退出條件，不通過重疊排期把真實工作量壓縮成不可信日期。專項與硬件矩陣很大時，M5 可拆成多個後續版本，不強行塞入同一髮布窗口。

<a id="4-m0形成可执行基线"></a>

## 4. M0：形成可執行基線

<a id="交付物"></a>

### 交付物

- 首期模型：固定文本模型和 tokenizer revision；訓練與推理使用可互相驗證的源版本。
- 首期設備：具體 Apple 型號／內存、NVIDIA 型號／顯存、系統和驅動。
- 桌面殼與 Python 側進程啓動、退出、崩潰、重啓試驗。
- 一條真實推理和一條最小訓練命令的運行記錄；這裡只用於驗證選型，尚不是產品閉環。
- 能力聲明初版、提交快照 schema、任務狀態機和存儲佈局。
- ADR 中需要拍板的選型結論與有證據的替代方案。

<a id="停止调整条件"></a>

### 停止／調整條件

若目標模型無法加載、驅動不兼容或打包依賴無法穩定復現，先調整該組合，不繼續在前端標記支持。若 Tauri 宿主延緩核心驗證，可臨時使用本地 Web 界面驗證合同；桌面產品決策單獨記錄。

<a id="5-m1应用和持久化基础"></a>

## 5. M1：應用和持久化基礎

將最終 Demo 轉為正式組件，保持四類入口、模型庫、數據市場、實驗室和 AI 面板。建立項目、任務、數據、模型和作品的數據庫結構；支持安全的文件選擇、導入、元信息和草稿保存。

實現任務狀態、事件流、冪等提交和假執行器。假執行器僅用於開發與測試，模式必須顯式，不作為真實模型支持證據。

退出驗收：殺掉控制服務後重啓，草稿和索引仍在；長任務狀態可恢復；錯誤能定位；跨項目後台結果不串入當前項目；文件損壞與磁盤不足有可恢復處理。

<a id="6-m2真实推理与参数生效"></a>

## 6. M2：真實推理與參數生效

先完成一個 Apple 本地文本推理適配器和一個 NVIDIA 服務推理適配器。實現模型準備、加載、卸載、輸入處理、流式輸出、取消、結果保存、實際參數記錄和配方重載。

開放經過驗證的思考開關、上下文、輸出上限和採樣參數；KV、前綴緩存和調度先選擇少量可測組合。其餘高級選項保留說明和未驗證狀態，不急於全部開放。

退出驗收：輸入／輸出 token 預算正確；後端確實採用配置；配方重載能說明環境差異；斷網本地推理、遠端中斷、取消後資源釋放通過。

<a id="7-m3训练与评测闭环"></a>

## 7. M3：訓練與評測閉環

實現 SFT + LoRA 的數據檢查、訓練、檢查點、恢復、獨立評測、候選登記和直接試用。增加 QLoRA 或全參數路徑前，先鎖定後端與硬件；不將“LoRA 能跑”視為其他更新方式已完成。

AI 輔助接入真實建議模型，但只開放已定義字段，完成預覽、應用、撤銷與衝突測試。首個內測版本在此階段形成，範圍限定於已經驗收的語言任務和設備。

退出驗收：真實數據 → 權重更新 → 獨立產物 → 評測 → 候選試用；失敗重試保留原任務；從檢查點恢復有一致性記錄；AI 無執行權。

<a id="8-m4媒体和工作流"></a>

## 8. M4：媒體和工作流

分別選一個圖片生成／微調組合、一個短視頻組合、一個語音或 ASR 組合，再逐步加入其他音頻任務。每類必須驗證真實文件讀取、真實產物和任務特有參數，不能用文本任務複製頁面替代。

實現“商品圖 → 視頻 → 配音”的結果傳遞、舊結果失效標記、階段重做和整體保存。數據市場至少接入一個可控來源，驗證受限訪問流程、版本、下載和原任務返回。

退出驗收：三步真實產物來源完整；圖像、視頻、音頻指標與人工檢查有對應報告；市場接口不可用時已下載數據仍可使用。

<a id="9-m5专项和多硬件"></a>

## 9. M5：專項和多硬件

按成熟度獨立推進量化、轉換、合併、蒸餾、行為調整。先選擇較小模型和可重復評測集，明確每項的輸入格式和產物，避免建立統一空殼後宣稱全部完成。

AMD／ROCm、Intel／SYCL、OpenVINO／NPU、Core ML／ANE 逐條加入設備矩陣。MTP 與 DFlash 使用已配套的目標模型、組件和版本，完成優化開／關對照。Prefill／Decode 分離若不具備部署條件，作為獨立延後工作包，不阻塞其他優化。

退出驗收：每個對外開放組合都有支持範圍、限制、測試樣本和報告；不能驗證的組合保持未驗證或不支持。

<a id="10-m6稳定化与发布"></a>

## 10. M6：穩定化與發佈

凍結候選版本後執行乾淨機器安裝、升級／回滾、數據庫遷移、備份恢復、長任務、磁盤滿和網絡故障測試。真實模式中不存在預置成功報告、模擬連接捷徑或偽造進度。

按實際支持矩陣編寫用戶手冊和發行說明，附安裝包身份、依賴版本、已知問題、恢復方法和兼容性清單。發佈動作與準備發佈包分別驗收。

<a id="11-版本建议"></a>

## 11. 版本建議

| 版本 | 階段門檻 | 範圍 |
| --- | --- | --- |
| 技術預覽 | M0—M2 的縱向驗證完成 | 內部驗證，不能稱完整產品 |
| 私有 Alpha | M3 | 語言訓練／試用閉環，限定硬件 |
| 功能 Beta | M4 + 選定 M5 工作包 | 媒體工作流、部分專項與擴展適配 |
| 首個正式版本 | M6，且目標矩陣全部有證據 | 按已驗收範圍發佈，未完成項清楚列出 |

<a id="12-依赖与关键路径"></a>

## 12. 依賴與關鍵路徑

關鍵路徑為：能力與快照合同 → 資產／數據庫 → 任務執行與恢復 → 真實推理 → 訓練與產物 → 獨立評測 → 候選試用 → 發佈驗收。

可以交錯推進的工作：數據導入器與前端表單、遠程執行器與本地推理、媒體解碼與專項模型來源核查。不能提前跳過的依賴：沒有固定數據版本不能做公平評測；沒有真實參數映射不能做優化測速；沒有產物完整性不能登記候選；沒有精確設備身份不能宣稱 ANE／ROCm／oneAPI 通過。

<a id="13-进度管理与变更控制"></a>

## 13. 進度管理與變更控制

每周按工作包更新：已完成證據、進行中內容、阻塞、下周交付，不只報告百分比。每個階段結束進行實際任務演示和測試報告評審。

新增模型或優化開關需要一張能力卡和相應測試成本。需求變更同時更新 PRD 編號、工作包、驗收用例和支持矩陣；發現更簡單且滿足目標的實現可以調整方案，但不能刪掉用戶已經確定的完整流程。

<a id="14-估算边界"></a>

## 14. 估算邊界

本計劃沒有取得團隊排班、設備預算或正式上線窗口。開始 M0 後用實際加載、訓練、打包和測試結果重估。若由單人實施，不能直接沿用上面的日曆週期；應縮減並行工作並以完整閉環為階段單位逐次承諾。
