<a id="1-工作包使用规则"></a>

## 1. 工作包使用規則

每個工作包必須有具體責任人、輸入版本、交付分支、測試記錄和評審結果。下表的責任是角色建議，不代表已經安排人員。規模使用 S／M／L：S 約 2—4 人日，M 約 5—8 人日，L 約 9—15 人日；硬件或算法驗證可能超出，應在技術試驗後拆分。

這些規模只用於比較任務體量，不能把所有行直接相加當作項目承諾。適配器工作包可能按模型、設備和版本重復展開。

<a id="6-重点工作包的可执行拆分"></a>

## 6. 重點工作包的可執行拆分

<a id="wp-07-能力查询"></a>

### WP-07 能力查詢

1. 定義參數 schema：類型、單位、默認來源、允許值、衝突、重啓要求。
2. 定義設備事實與版本摘要，支持探測失敗／未知值。
3. 為首期兩個引擎實現能力映射。
4. 前端根據 schema 生成可用選項，保留中文說明。
5. 提交端獨立執行同樣約束，返回實際參數。
6. 編寫不支持組合與靜默丟參測試。

完成條件：至少一個控件隨模型／引擎／設備變化而改變，後端能拒絕偽造請求，實際執行記錄與表單一致。

<a id="wp-12-训练闭环"></a>

### WP-12 訓練閉環

1. 將真實 JSONL 解析為固定數據版本，生成檢查報告。
2. 按來源組劃分訓練與驗證，固定種子。
3. 將 SFT + LoRA 參數映射到指定訓練庫版本。
4. 將步驟、損失、檢查點和故障寫為持久事件。
5. 驗證取消、失敗、新嘗試與檢查點恢復。
6. 輸出獨立適配器文件，並從乾淨進程加載。

完成條件：優化步驟確實更新了目標參數，產物可加載，原始模型／數據哈希保持不變；不能以退出碼 0 代替這些檢查。

<a id="wp-17-推测解码"></a>

### WP-17 推測解碼

按策略拆成三個子任務，每個單獨選擇目標模型和組件。先測標準解碼基線，再測開啓策略；固定模型、精度、輸入長度、輸出長度和併發。保存接受率、總延遲和質量對照；無收益也允許結論為不建議默認開啓。

<a id="wp-24-转换与-ane"></a>

### WP-24 轉換與 ANE

先確認輸入格式和形狀，建立數值對照樣例；轉換後獨立加載，再在目標設備運行。Core ML 計算單元策略與實際運行分配分別保存。不能取得 ANE 分配證據時，報告只能說 Core ML 執行通過。

<a id="7-每张开发任务卡必须包含"></a>

## 7. 每張開發任務卡必須包含

目標、需求編號、輸入資料、具體實現範圍、明確不處理的相鄰事項、依賴、交付文件、錯誤情形、自動測試、真實操作步驟、性能／數據邊界、完成證據、審查人。

任務狀態採用待開始、進行中、待評審、待驗收、完成、阻塞。只有測試和所需實機證據齊全才進入完成。功能被延期時保留需求和原因，不刪除追蹤編號。

<a id="8-第一批可启动任务"></a>

## 8. 第一批可啓動任務

先安排 WP-01 與 WP-02 的技術試驗，再根據結果完成 WP-03、WP-06、WP-07 合同；WP-04 與 WP-05 可在合同穩定後交錯推進。不要在任務、版本和能力模型未確定前同時接入全部模型庫。

本輪沒有創建開發分支、安裝環境或運行真實訓練。以上工作包是後續開工使用的完整任務基線。
