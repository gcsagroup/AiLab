<a id="1-工作包使用规则"></a>

## 1. 工作包使用規則

每個工作包必須有具體責任人、輸入版本、交付分支、測試記錄和評審結果。下表的責任是角色建議，不代表已經安排人員。規模沿用 1.0 的相對體量 S／M／L；原參考為 S 約 2—4 人日、M 約 5—8 人日、L 約 9—15 人日。1.1 新增的異常恢復、導出、跨端和負例成本尚待 M0 實測後重估，不能把原體量當成新增內容已經包含的承諾。

頂層保留 WP-01—WP-30。跨階段工作按第 6 節子項獨立安排；子項是原工作包拆分，不是新增頂層模塊。階段驗證列給出當前階段可執行的門檻；最終 AC 列只追蹤完整產品驗收，**不要求早期工作包提前完成最終 AC 的全部內容**。階段任務卡必須列出 [11 的階段門檻](11-testing-and-acceptance.md) 中與本行交付物對應的子集及執行條件。

每個工作包的完成證據只適用於已驗證模型、設備、版本和功能範圍。未開放組合標記未測或延期，不能借階段子集將完整 AC 標記通過。下表所有規模均待重新估算，適配器仍需按實際組合展開。

## 7. 重點工作包的可執行拆分

<a id="wp-06状态控制与只补收"></a>

### WP-06：狀態控制與只補收

1. 從 [07](07-api-and-task-lifecycle.md) 的狀態表逐行生成正常、失敗、超時和競爭測試；暫停檢查點失敗、暫停中取消、取消中崩潰、finalizing 中取消均有出口。
2. 暫停／恢復／取消／強制停止採用狀態版本和冪等鍵，重復事件只裁決一次；無停止證據保留 `stop_status=unknown`，不偽報資源已釋放。
3. 計算結果與收集記錄獨立。補收引用原嘗試產物清單，校驗、傳輸和登記均冪等；不得調用 `run`／`resume`，不得改變原 RunAttempt 終態。
4. M1 使用假執行器和真實文件／數據庫完成合同故障測試，M2／M3 接入真實適配器後重跑對應分支。

<a id="wp-07能力与配置一致"></a>

### WP-07：能力與配置一致

1. 定義參數類型、單位、默認來源、允許值、衝突、重啓要求與組合版本。
2. 綁定模型、基座／適配器、策略組件、引擎、設備、格式、任務模式和輸入媒體能力；準備狀態屬於確定組合。
3. 變更任一依賴時重算有效性，顯示需要清除／重置的字段，取消不改已應用設置。
4. 前端和提交端各自校驗；覆蓋普通草稿與 DFlash 雙向切換、Omni 音頻到視覺模型、Core ML 格式到不支持引擎的偽造提交。
5. 通過適配器回讀實際參數；默認配置只能初始化新草稿，執行摘要與按鈕旁位置使用已應用快照。

完成條件：界面、應用配置、請求快照與後端實際值一致，未知組合不能準備或執行；M1 合同通過不等於 M5 所有策略已實機支持。

<a id="wp-12监督目标与训练闭环"></a>

### WP-12：監督目標與訓練閉環

1. 解析真實 JSONL 並固定數據版本，按來源分組劃分訓練／驗證，固定種子。
2. 保存 tokenizer、processor、模板與監督配方版本，固定 assistant-only／completion-only、EOS／PAD、截斷和 packing 邊界策略。
3. 為多輪、超長、空回答、僅系統消息、padding、拼接與多模態輸入核對最終 tokens／labels；統計有效監督 token、截斷／丟棄，零監督樣本拒絕進入數據劃分，訓練集或必需驗證集過濾後無有效監督則阻斷任務。
4. 將 SFT + LoRA 映射到指定訓練庫版本，記錄真實優化步、損失、檢查點和故障事件。
5. 驗證取消、失敗新嘗試、檢查點恢復和只補收；從乾淨進程加載獨立適配器，再完成目標設備試用。

完成條件：目標參數確實更新、原始模型／數據摘要不變、實際產物可加載且證據鏈完整；退出碼 0 或損失下降均不能單獨替代這些檢查。

<a id="wp-17wp-24组合与产物适配"></a>

### WP-17、WP-24：組合與產物適配

推測解碼按普通草稿、MTP、DFlash 拆為策略子任務；固定目標、組件、模板、思考條件、精度與併發，比較標準基線。切換使錯誤配套準備失效，準備前後及提交時都復核。保存接受率、總延遲和質量，無收益允許結論為不建議默認開啓。

量化／轉換先驗證輸入格式和形狀，建立數值對照；轉換候選默認引擎依據實際格式選擇，不能繼承不適用來源配置。從候選入口獨立加載，兩個錯誤格式／引擎方向都阻斷。Core ML 策略與實際分配分別保存，無 ANE 證據只能說 Core ML 執行通過。

<a id="wp-21每轮工作流和原子推进"></a>

### WP-21：每輪工作流和原子推進

為每次 WorkflowRun、步驟嘗試和輸入版本固定編號；默認只接受當前輪當前步驟當前輸入的產物，復用舊結果要明確操作並記錄來源。修改上游輸入後舊下游產物標記失效。目標類別可進入性檢查、步驟推進、輸出引用和目標草稿寫入放在同一裁決事務中；檢查失敗全部不變。

復測兩輪完整流程、第二輪零次生成、修改上游、目標運行／暫停／剛完成／剛取消及雙擊推進；失敗提供查看阻塞任務、等待或退出，解除阻塞後只推進一次。

<a id="wp-29用户导出与发布分工"></a>

### WP-29：用戶導出與發佈分工

後端負責對象選擇計劃、依賴解析、manifest、摘要、部分文件與登記事務；前端負責範圍／大小／依賴提示、保存位置、進度、取消和恢復；平台負責目標路徑、權限與 M6 安裝更新。正式指派人員時每項只有一個責任人，協作角色不能替代負責人。

模型、適配器、作品、報告各有真實樣例。適配器包含固定基座依賴及缺失提示；不默認捆入無權分發的基座。媒體可獨立打開；報告引用模型、數據、規則、結果和版本；結果修訂保留原生成配方。缺文件、磁盤滿、取消和校驗失敗不能產出偽完整包，恢復只處理導出，不觸發模型重算。診斷包和普通用戶產物包是不同導出類型。

<a id="8-每张开发任务卡必须包含"></a>

## 8. 每張開發任務卡必須包含

目標、PRD／AUD／E 對應關係、輸入版本、實現範圍、依賴子項、交付文件、階段驗證子集、最終 AC 追蹤、錯誤情形、自動測試、真實操作步驟、性能／數據邊界、完成證據和審查人。

任務狀態採用待開始、進行中、待評審、待驗收、完成、阻塞。只有本階段約定測試和實機證據齊全才進入階段完成；最終 AC 在完整適用範圍執行後單獨簽署。功能延期時保留需求、組合和原因，不刪除追蹤編號。

WP-30 從各階段維護文檔關係檢查與負測，M6 匯總用戶驗收。檢查 PRD → 工作包 → AC 的具體行關係、缺交付對象、參考週期求和、依賴子項和階段倒掛；審計資產固定清單／摘要／復跑命令，保留歷史來源，不把“成功復現已知問題”當產品測試通過。

<a id="9-第一批可启动任务"></a>

## 9. 第一批可啓動任務

先收斂 [16 的整改合同](16-audit-remediation-plan.md)，再安排 WP-01、WP-02，以 TV-01—TV-03 獨立退出。依據試驗結果安排 WP-03、WP-06、WP-07a；WP-04、WP-05 可在合同穩定後交錯推進。M0 不需要等待 M3 導出器或 M6 安裝、升級與完整硬件驗收。

本輪更新規範和計劃，不代表上述產品實現已經完成；後續按階段門檻逐項執行並保存證據。
