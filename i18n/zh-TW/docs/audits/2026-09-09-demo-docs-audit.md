# 最終 Demo 與產品開發文檔審計

日期：2026-09-09 · 對象：最終整合 Demo 與 1.0 版的 17 份中文文檔。

<a id="1-结论与处理范围"></a>

## 1. 結論與處理範圍

**產品結構可以保留，當前文檔可以支持 M0 技術試驗，但還不適合直接凍結為正式開發和驗收合同。** 本輪確認 14 項問題：6 項 Demo 行為錯誤、5 項技術合同遺漏、3 項開發與驗收問題。其中 4 項列為 P1，10 項列為 P2；另外提出 5 項增強建議。沒有發現需要推翻四類工作台、模型庫、數據市場或模型實驗室的依據。

P1 表示應優先修正的流程完整性或階段放行問題；P2 表示應在相關模塊實施前補齊的問題。這裡的等級服務於本次審計，不是對不存在的真實後端進行漏洞評級。

本輪只增加審計報告與獨立復現腳本。未改原 Demo、原 17 份文檔、構建腳本或原測試；未安裝模型、驅動或後端，未部署服務。下列建議尚未實施，不能讀作“問題已修復”。

<a id="11-已有设计中应保留的部分"></a>

### 1.1 已有設計中應保留的部分

- 四類訓練／試用／歷史圍繞同一類別展開，入口和返回位置較清楚。
- 訓練類型與參數更新方式分別建模；運行設置先編輯、檢查、應用，再由用戶執行。

- 項目歸屬、不可變執行快照、數據版本、候選評測和 AI 人工應用邊界已有基礎規範。

## 3. Demo 行為問題

<a id="aud-01同一工作流重新开始后旧结果可以直接推进"></a>

### AUD-01：同一工作流重新開始後，舊結果可以直接推進

**位置：**[最終 HTML 第 323 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-unified.html:323>)；配套 `ailab-unified-ui.js` 第 20、71、72 行。

**瀏覽器復現：**載入“商品圖 → 視頻 → 配音”，第一步生成香水圖 GEN-41；退出工作流後重新載入，把提示詞改成“紅色茶壺，純白背景”，沒有生成新圖就點擊“帶入下一步”。界面成功進入第 2 步，參考圖仍顯示“來自 GEN-41”。

獨立反例進一步完成了兩輪三步流程：第二輪新增生成任務數為 0，仍可保存完整工作流，輸出編號與第一輪完全相同。工作流只保存定義編號，沒有本次執行編號；結果選擇為空時會退回歷史第一項，下一步僅檢查模型與工作流定義。

**影響：**用戶以為新輸入已經生效，實際後續步驟繼續使用舊圖。顯式復用舊結果可以是功能，但當前沒有這一步選擇和來源確認。

**最小修改：**工作流執行、步驟嘗試與輸入版本分別編號；下一步默認接受當前執行當前步驟的產物。復用舊結果須有明確動作和記錄。修改輸入後展示舊結果的來源狀態。

**驗收：**完整執行兩輪；第二輪未生成時不得直接成功；顯式復用時記錄來源；修改第一步後下游舊產物標記失效。

**與已知差距的關係：**14 已記錄“舊輸入失效／重做”待實現，但未具體披露新一輪可以零次生成就保存。此處是新增實證，不是重復報告預置圖片 GAP-03。

<a id="aud-02目标类别有任务时步骤推进不是完整事务"></a>

### AUD-02：目標類別有任務時，步驟推進不是完整事務

**位置：**[最終 HTML 第 323 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-unified.html:323>)；配套 `ailab-unified-ui.js` 第 69、72 行。

**觸發：**先生成並暫停一個視頻任務，再載入商品工作流並完成圖片，點擊“帶入下一步”。代碼先加入輸出並增加步驟，隨後切換到視頻頁時才發現視頻類別有任務，拒絕切換。後續代碼仍繼續修改當前草稿。

**反例結果：**工作流處於第 2 步，但當前類別仍為圖片；圖片草稿的來源被設為自己剛生成的圖片編號。界面提示類別有任務，卻已經變更步驟，繼續操作會卡在不一致狀態。

**最小修改：**先完成目標類別可進入性檢查，再一次性提交步驟、輸出和新草稿引用。失敗保留原步驟，並提供查看阻塞任務、等待或退出的明確動作。

**驗收：**目標任務運行中、暫停中、剛好完成、剛好取消四種條件；失敗時步驟、輸出集合、源草稿均不變，解除阻塞後一次點擊只推進一次。

<a id="aud-03切换推测策略时没有清除不兼容草稿"></a>

### AUD-03：切換推測策略時沒有清除不兼容草稿

**位置：**[運行狀態邏輯第 18 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-runtime-state.js:18>)及第 21 行；對應最終 HTML 第 229、232 行。

**瀏覽器復現：**Qwen3-4B → 雲 GPU／vLLM → 關閉思考 → 普通草稿 → 選擇並模擬準備草稿 → 只切換策略為 DFlash。界面仍顯示“演示組件已準備”，可以應用、發送並完成 GEN-42。

結果配方實際記錄：

```json
{"speculation":"dflash","draftModel":"qwen4-draft","draftReady":true}
```

當前 DFlash 選項對應 `qwen4-dflash`。準備是否真實並不是本問題的關鍵；現有靜態配對關係本身已經不一致。

**最小修改：**策略改變時清除不匹配的草稿和準備狀態；應用與提交均重新驗證目標模型、策略、組件編號和引擎。準備狀態應屬於一個確定組合，不能是獨立布爾開關。

**驗收：**普通草稿與 DFlash 雙向切換，準備前後切換模型／引擎，以及直接提交舊配置；所有不匹配組合均阻斷。

<a id="aud-04模型切换后界面显示与实际任务类型不同"></a>

### AUD-04：模型切換後，界面顯示與實際任務類型不同

**位置：**[界面事件第 89 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-unified-ui.js:89>)、第 24 行及 `ailab-unified-state.js` 第 35 行。

**瀏覽器復現：**準備 Qwen Omni，選擇音頻理解與示例素材；換成 Qwen2.5-VL-3B。下拉框顯示“看圖問答”，已經沒有音頻理解選項；直接發送卻完成 GEN-44，並顯示“轉寫：歡迎來到聲音工作台”。

獨立反例確認提交值仍為 `mode=audio`，模型為 `qwen-vl`。原型自己的模型清單只給這個模型聲明文本、圖片和視頻輸入。

**最小修改：**換模型後重新校驗任務類型、素材類型和輸出方式；無效項明確重置並展示變更。提交校驗不能依賴下拉框當前可見選項。

**驗收：**音頻能力模型切到純視覺模型；反向切換；帶參考視頻、圖片、錄音的切換；界面選中值與提交快照逐項相同。

<a id="aud-05转换后的格式没有参与默认运行引擎选择"></a>

### AUD-05：轉換後的格式沒有參與默認運行引擎選擇

**位置：**[運行默認值第 14 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-runtime-state.js:14>)及第 15、19 行。

**反例：**圖像融合網絡轉換為“運行模型 · Core ML FP16”並登記後，直接運行候選。默認值為 `pytorch / metal`，校驗沒有錯誤，生成任務被接受。

當前檢查只阻止 Core ML 引擎使用非 Core ML 產物，沒有反向檢查其他引擎是否支持轉換產物。不能據此聲稱已有真實加載失敗；本次證明的是演示合同接受了自身未建立有效加載路徑的組合。

**最小修改：**產物格式參與默認引擎選擇和最終加載能力檢查；候選繼承來源信息時，不繼承已經不適用的運行配置。需要橋接時將橋接步驟列為獨立準備動作。

**驗收：**轉換產物從“候選 → 運行”入口真實經過完整選擇鏈；正確格式和引擎通過，錯誤方向均阻斷。不能僅測試“原始權重不能用 ANE”一個方向。

<a id="aud-06执行位置提示与已应用配置来自不同来源"></a>

### AUD-06：執行位置提示與已應用配置來自不同來源

**位置：**[試用表單第 24 行](</Users/lazy/.codex/visualizations/2026/09/07/01a07c7f-b284-7b41-9a2e-0f2282b08162/ailab-unified-ui.js:24>)；最終 HTML 第 275 行。

**瀏覽器復現：**保留全局默認本機，在單次運行設置里選擇雲 GPU 並應用。參數摘要顯示 vLLM／NVIDIA CUDA，發送按鈕旁卻仍顯示“本機 Apple Silicon · 演示執行”。結果配方中的設備為 `cloud`，環境名稱為“雲 GPU 實例”。

**最小修改：**本次執行摘要、按鈕提示、發送範圍和提交快照統一讀取已應用配置。全局默認只用於創建新草稿。

<a id="4-技术合同遗漏"></a>

## 4. 技術合同遺漏

<a id="aud-07暂停和取消中途出现异常时没有闭合处理"></a>

### AUD-07：暫停和取消中途出現異常時沒有閉合處理

**位置：**[07 任務狀態機](../07-api-and-task-lifecycle.md)第 129—144 行；控制接口第 44—47 行；取消說明第 174 行。

狀態圖中 `pausing` 只能進入 `paused`，沒有寫檢查點失敗或暫停時再次取消的出口；`cancelling` 只有執行器確認停止後的成功出口。正文提到強制終止入口，卻未給相應命令、結果和狀態合同。

對狀態圖進行代表性序列檢查，確認未表達 `pausing→failed`、`pausing→cancelling`、`cancelling→failed`。實際設計可以選擇回到運行、保留待確認狀態等其他策略，關鍵是明確約定每個事件的結果；不是要求機械增加這三條邊就算修復。

**最小修改：**補狀態轉移表與可用動作，覆蓋暫停失敗、暫停時取消、取消時崩潰、超時強制終止和停止結果未知。控制命令統一版本檢查、冪等與錯誤反饋。

**驗收：**逐事件表驅動檢查，加取消／完成競爭、重復控制、斷連補拉；沒有執行器證據時不能顯示已停止。

**已有覆蓋：**07 已定義安全點、取消確認、連接狀態與運行狀態分離；11 已有一般故障測試。本問題是這些規則在異常分支上沒有閉合，不能概括為“完全沒有恢復設計”。

<a id="aud-08产物补收与计算重试混在一起"></a>

### AUD-08：產物補收與計算重試混在一起

**位置：**[12 運維](../12-operations-and-release.md)第 57、62 行；[07 接口](../07-api-and-task-lifecycle.md)第 47、137—143、178 行；[06 適配器](../06-architecture-and-adapters.md)第 92 行。

運維文檔允許磁盤滿後“重試收集”；執行器已有 `collect`。但狀態合同將收集／登記失敗歸為執行失敗終態，公開重試動作只會建立新的計算嘗試草稿，沒有僅補傳文件、校驗並登記的操作。

**影響：**訓練已經完成、遠端文件完整，僅本地寫入失敗時，團隊沒有明確實現路徑來恢復成果而不重跑訓練。

**最小修改：**分開計算結果和收集狀態，或新增冪等補收操作並引用原產物清單。保留原嘗試記錄，不把補收成功偽裝成重新計算。

**驗收：**計算完成後磁盤滿、傳輸中斷、登記事務失敗；恢復後計算調用次數不增加，文件摘要一致、資產登記一次。

<a id="aud-09多模态前缀缓存缺媒体身份条件"></a>

### AUD-09：多模態前綴緩存缺媒體身份條件

**位置：**[04 緩存規範](../04-runtime-and-hardware.md)第 69 行。

最小緩存鍵列出模型、適配器、tokenizer、模板、token 前綴、精度和隔離範圍，但沒有媒體內容摘要、處理器和預處理參數。相同問題配不同圖片時，媒體佔位 token 可能相同。vLLM 官方專門用圖片哈希區分此情況。[官方說明](https://docs.vllm.ai/en/latest/design/prefix_caching/)

**最小修改：**緩存身份納入媒體內容或編碼結果、媒體順序、處理器版本及裁剪／抽幀等參數。若交由底層引擎管理，應要求適配器確認這些條件；不能另建弱化的應用層緩存。未知組合保持關閉。

**驗收：**相同文字、不同圖片／視頻／音頻不能錯誤命中；相同媒體改變裁剪、順序或處理器版本後正確失效。

**邊界：**項目尚無真實緩存實現，本項是會影響正確性的設計遺漏；04 已有媒體 token 預算和項目隔離規範。

<a id="aud-10sft-数据通过结构检查不代表监督目标已确定"></a>

### AUD-10：SFT 數據通過結構檢查，不代表監督目標已確定

**位置：**[03 訓練參數](../03-training-and-model-lab.md)第 53 行；[05 數據樣例與檢查](../05-data-model-and-assets.md)第 65、136、160 行。

文檔保存了 messages、模板與 tokenizer 版本，但沒有固定哪些 token 參與損失計算、EOS／PAD、截斷方向、樣本拼接和邊界策略。不同適配器可能對同一數據訓練不同目標；超長樣本可能留下問題卻丟掉回答。

TRL 將 assistant-only、completion-only 與 packing 分別定義，並對聊天模板提出具體要求。[官方說明](https://huggingface.co/docs/trl/sft_trainer)

**最小修改：**增加版本化的分詞和監督配方；可用訓練模板固定策略，不必把每項都變成普通用戶要填寫的參數。展示有效監督 token、截斷和丟棄樣本統計。

**驗收：**多輪對話、超長回答、空回答、只有系統消息、padding、拼接邊界與多模態樣本；核對最終 token 與 labels，零有效監督樣本拒絕訓練。

<a id="aud-11模型格式的执行风险没有进入导入合同"></a>

### AUD-11：模型格式的執行風險沒有進入導入合同

**位置：**[06 環境與信任邊界](../06-architecture-and-adapters.md)第 127、131 行；[07 模型導入計劃](../07-api-and-task-lifecycle.md)第 25 行；[05 模型版本](../05-data-model-and-assets.md)第 160 行。

文檔已將自定義倉庫代碼執行作為獨立信任決定，但沒有覆蓋第三方 pickle、TorchScript 和檢查點加載方式。哈希正確且沒有運行倉庫腳本，不代表加載模型文件沒有執行風險。PyTorch 明確要求把未知 TorchScript 按可執行代碼處理，並區分序列化格式的風險。[官方政策](https://github.com/pytorch/pytorch/security/policy)

**最小修改：**導入計劃記錄加載方式與信任類別；常規權重採用允許格式和受限加載，失敗時不得自動降級為任意反序列化。需要執行代碼的格式單獨決定，並限制可訪問文件、網絡和憑證。

**驗收：**受限加載失敗、格式偽裝、不受信任檢查點、需要自定義代碼的模型；驗證拒絕、明確提示和隔離。依賴環境隔離不能替代執行權限隔離。

**邊界：**這是設計合同審計，沒有嘗試執行惡意模型，也沒有證明當前應用存在真實代碼執行漏洞。

### AUD-12：M0 技術試驗綁定了後期產品驗收

**位置：**[10 工作包](../10-work-breakdown.md)第 17—20、59—61、99 行；[11 驗收](../11-testing-and-acceptance.md)第 48、92、132 行。

WP-02 屬於 M0，交付桌面殼與側進程試驗，卻要求 AC-01 和 AC-22。AC-01 包括雙項目數據庫草稿／歷史重啓恢復，主要存儲到 M1 才建；AC-22 包括候選安裝包、升級、遷移回滾、備份恢復和導出，相關工作包在 M6。WP-04 又依賴 WP-02，工作包完成標準要求相關測試齊全。

**影響：**按照任務卡執行，M0 沒有獨立可判定的退出門檻。團隊可能提前勾選最終驗收，也可能因等待後期工作而無法推進。WP-01 對完整硬件 AC-12 的引用也需要分階段解釋。

**最小修改：**為 M0 建立技術試驗驗收，或將 AC 明確拆成階段子項，區分“本階段試驗通過”和“完整產品驗收通過”。最終驗收保留在對應交付階段匯總。

**驗收：**每個 M0 工作包可以只依賴當階段交付物完成；依賴圖無階段倒掛，驗收子項都有明確執行條件。

### AUD-13：普通產物導出沒有明確負責人和交付物

**位置：**[01 PRD-019](../01-product-requirements.md)第 77 行；[07 導出準備接口](../07-api-and-task-lifecycle.md)第 52 行；[12 導出包](../12-operations-and-release.md)第 90 行；[14 對照](../14-prototype-traceability.md)第 62 行；[10 工作包](../10-work-breakdown.md)第 50、60 行。

**最小修改：**在現有工作包中明確負責人、階段和導出器範圍：選對象、解析依賴、清單、打包落盤、完整性、失敗恢復及獨立環境使用。沒有必要為了編號再新建一個大模塊。

**驗收：**四類導出對象各有樣例；適配器包含基座依賴；媒體可獨立打開；評測報告可追蹤；缺文件或取消時不產出偽完整包。

## 6. 建議增強的五個方向

這些建議尚未列入已確認缺陷數量；應按成本和產品目標取捨，不應因此無限擴張首期範圍。
