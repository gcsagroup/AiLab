# 產品需求規格

版本：1.1 · 日期：2026-09-09 · 狀態：最終 Demo 與審計修訂後的產品規範；真實實現及 Demo 缺陷修復待執行。

相關文檔：[交互流程](02-user-flows-and-ui.md)、[開發路線](09-development-roadmap.md)、[原型證據](14-prototype-traceability.md)。

<a id="1-产品定位"></a>

## 1. 產品定位

GCSA-AiLab 是本地優先的模型訓練、後訓練與運行工作台。用戶圍繞一個實際目標組織模型、數據、執行環境、實驗、評測和產物，完成從準備到試用的連續任務，而不是在互不關聯的工具頁面之間搬運文件。

產品同時覆蓋語言與多模態模型、圖片模型、視頻模型和音頻模型。訓練和生成不是兩個相互割裂的產品：用戶可直接試用已有模型，也可以從訓練得到候選，再用同一套輸入和配方比較效果。模型庫承擔選擇、準備與運行入口；工作台承擔當前任務；模型實驗室承擔專項處理；作品與素材承擔內容復用。

<a id="2-目标用户与关键任务"></a>

## 2. 目標用戶與關鍵任務

| 用戶 | 當前困難 | 本產品要完成的任務 | 成功的可觀察結果 |
| --- | --- | --- | --- |
| 本地模型使用者 | 參數和後端分散，不知道組合是否適用 | 選擇模型與設備，調整上下文、思考與緩存並運行 | 能解釋本次實際設置，結果保留輸入與配方 |
| 模型微調開發者 | 數據、訓練、評測和適配器來源容易混淆 | 使用明確的數據版本完成微調、評測、登記、試用 | 候選可追溯到源模型、數據和執行環境 |
| 多媒體創作者 | 圖像、視頻、聲音之間難以接續 | 從素材生成圖片，再生成鏡頭與配音 | 每一步有獨立結果，工作流來源鏈完整 |
| 算法研究人員 | 多個實驗不能公平比較，失敗記錄易丟失 | 蒸餾、合併、量化、轉換或行為調整對照 | 各候選獨立執行和評測，失敗可復現 |
| 自有算力維護者 | 多硬件環境的驅動與引擎能力不透明 | 管理本機、服務器、雲實例，檢查適配組合 | 能區分可連接、可加載、可執行與已驗收 |

<a id="21-核心用户故事"></a>

### 2.1 核心用戶故事

- 作為微調開發者，我希望先選擇任務目標與數據，再確認 SFT + LoRA 等組合，避免把方法名稱當成互斥類別。
- 作為本地用戶，我希望關閉思考和限制上下文後看到實際生效的參數，而不是僅隱藏界面上的思考文本。
- 作為多媒體用戶，我希望保存圖片後直接帶入視頻，並在視頻結果中找到來源圖片。
- 作為研究人員，我希望原始失敗實驗保留，新嘗試有獨立編號，不能被“重試成功”覆蓋。
- 作為設備維護者，我希望界面說明某項優化缺少什麼，而不是把全部選項都顯示為可用。
- 作為數據使用者，我希望自行記錄來源和使用範圍，AI 可以整理材料，但不替我作授權結論。

<a id="3-产品目标与不纳入首期的范围"></a>

## 3. 產品目標與不納入首期的範圍

<a id="31-必须实现的目标"></a>

### 3.1 必須實現的目標

1. 任務閉環：準備 → 執行 → 檢查 → 保存；訓練進一步支持評測 → 登記候選 → 試用。
2. 配方可追溯：記錄輸入、模型版本、訓練或運行參數、數據版本、環境和結果。
3. 本地優先：沒有遠程服務時，已經準備好的本地模型仍可完成適用的本地任務。
4. 多硬件可解釋：可見設備、引擎、格式和版本限制，按驗證記錄顯示能力。
5. 人工控制：AI 建議必須先預覽，用戶應用後才修改，執行必須是單獨的用戶動作。
6. 增量接入：保留四類產品結構，但按照真實可交付的模型與設備組合逐步實現。

<a id="32-不纳入首个内测闭环"></a>

### 3.2 不納入首個內測閉環

- 從零預訓練通用大模型和大規模跨機訓練平台。
- 無人工確認的自主實驗代理、自動雲實例採購或自動對外發佈。
- 自營數據交易結算、訂單支付、結算分成、合同簽署系統。
- 面向組織的完整多人協同、細粒度組織權限、企業 SSO。
- 承諾所有模型、所有硬件、所有精度和所有加速方法任意組合可運行。

這些邊界不刪除 Demo 中的產品入口。未實現的真實能力必須明確顯示“待接入”或“待驗證”，並給出可繼續完成的路徑。

<a id="5-通用业务规则"></a>

## 5. 通用業務規則

<a id="51-对象归属"></a>

### 5.1 對象歸屬

項目包含任務、配方、評測與作品引用。模型文件和公開數據文件可以在物理存儲中去重，但項目可見性、來源聲明和緩存範圍不能由去重自動擴大。後台任務提交時固定歸屬，完成時不能根據當前頁面的項目寫入結果。

<a id="52-修改与执行分离"></a>

### 5.2 修改與執行分離

編輯表單不等於運行。運行設置彈窗先保存修改草稿，“檢查並應用”只把配置寫入當前任務；“開始訓練”或“發送／生成”才提交執行。配置變更不得隱式購買資源、下載新組件或替換正在運行的模型。

<a id="53-有效参数不能只停留在表单"></a>

### 5.3 有效參數不能只停留在表單

服務端校驗並返回 `effective_config`（實際執行配置）。如果用戶請求的設置不被引擎支持，應拒絕或顯式請求用戶選擇替代方案，不得默默忽略。引擎自動值必須被解析或明確標為“由引擎動態決定”。

<a id="54-失败是可保留结果"></a>

### 5.4 失敗是可保留結果

任務失敗要保存輸入、配置、環境、日誌、錯誤分類和最近可用檢查點。重試默認新建嘗試並關聯舊任務；恢復檢查點則明確展示從哪個步驟繼續。失敗候選可以保留為研究記錄，但不能通過“登記可用候選”入口混入正常模型庫。

<a id="55-评测和发布分别决定"></a>

### 5.5 評測和發佈分別決定

訓練完成只表示執行結束，評測通過只表示指定評測範圍達標，登記候選只表示可進入後續試用。導出成功、目標設備加載通過、發佈完成是另外三種狀態，各自需要證據。

<a id="56-可见选择与实际执行一致"></a>

### 5.6 可見選擇與實際執行一致

模型、任務模式、輸入素材、產物格式、引擎、設備和優化組件必須一起校驗。改變上游選擇時，先在草稿中標明失效項與替代值，再由用戶應用；不能保留界面已經不可見的舊選項繼續提交。準備狀態綁定精確組件與環境版本，不能跨策略繼承一個“已準備”布爾值。執行位置、數據發送目的地、運行摘要與提交快照必須來自同一份已應用配置。

<a id="57-需求修订与实现状态分开"></a>

### 5.7 需求修訂與實現狀態分開

本輪 14 項審計問題已進入專項規範、工作包和驗收；5 項增強建議按限定範圍進入計劃。文檔處理完成不改變現有 Demo 的實現狀態。逐項狀態與需求追蹤以 [16 審計整改與需求追蹤](16-audit-remediation-plan.md) 為準。

<a id="7-成功指标与质量度量"></a>

## 7. 成功指標與質量度量

產品內測先度量可完成性：核心路徑完成率、首次結果耗時、任務恢復成功率、錯誤修正次數、配方復用成功率。業務側再度量模型質量和資源成本，不用下載數量或訓練次數替代成功率。

指標必須包含樣本數、測試條件和排除項。例如首次結果耗時分別記錄環境準備、下載、模型加載、Prefill 和 Decode；訓練耗時分別記錄預處理、加載、優化步驟、檢查點寫入與評測。不同硬件之間不得以不相同輸入或量化方式直接排名。

<a id="8-第一版真实闭环的放行定义"></a>

## 8. 第一版真實閉環的放行定義

首個內測版本至少在一個明確的 Apple 本地推理組合和一個明確的 NVIDIA 訓練組合上完成：真實導入數據、真實模型加載、SFT + LoRA 小樣本訓練、獨立評測、登記候選、候選試用、配方保存、應用重啓後恢復。其他類別和硬件繼續保留產品結構，但其狀態必須與驗收矩陣一致。

M0 先用同一份最小 LoRA 實物完成跨端技術試驗，核對基座、適配器模塊、模板和目標引擎，不等待產品導出器。M3 再通過正式產品入口完成同一鏈路；不能以兩端各跑一個無關模型代替。首次用戶路徑另設 AC-25，完整回程與導出分別對應 AC-26、AC-27。

完整覆蓋最終 Demo 的階段性目標見 [09](09-development-roadmap.md)，具體用例見 [11](11-testing-and-acceptance.md)。
