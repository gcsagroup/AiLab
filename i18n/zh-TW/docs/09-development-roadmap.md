# 開發路線、里程碑與資源計劃

版本：1.1 · 日期：2026-09-09 · 狀態：已按審計修訂範圍和階段門檻；真實開發尚未開始，週期待技術試驗後重估。

相關文檔：[工作包](10-work-breakdown.md)、[測試門檻](11-testing-and-acceptance.md)、[風險與決策](13-decisions-risks-and-questions.md)、[審計整改計劃](16-audit-remediation-plan.md)。

<a id="1-实施顺序"></a>

## 1. 實施順序

先打通真實任務與數據保存，再擴展模型和硬件；先證明一個完整組合，再增加優化開關。四類工作台和現有輔助入口保持不變，後端按階段接入。未接入功能顯示實際狀態，不把全部功能隱藏到一個無法評審的“未來版本”。

第一條真實路徑選擇語言模型推理及 SFT + LoRA 閉環。它覆蓋項目、模型、數據、設備、執行、評測、產物、試用、配方、恢復，能夠驗證共用架構。同一份 LoRA 產物在目標試用設備加載的風險前移到 M0 技術試驗，M3 再驗證完整產品路徑。隨後擴展媒體、專項實驗與多硬件，避免各模塊各建一套任務系統。

本版納入 AUD-01—AUD-14 的必要整改，並按最小範圍採納 E-01—E-05：首次用戶路徑、三類運行預設、跨端產物驗證、結果修訂版本、可復跑審計資產。當前修訂只完成規範和計劃，不代表原型問題已經修復或真實能力已經通過。

<a id="4-m0形成可执行基线"></a>

## 4. M0：形成可執行基線

<a id="先收敛文档合同"></a>

### 先收斂文檔合同

在技術試驗前統一工作流身份、配置聯動、任務控制異常、補收、監督配方、模型信任和導出歸屬；關係檢查能發現錯配與階段倒掛。這裡要求文檔可據以實施，**不要求 M0 完成這些模塊的產品後端**。原型 AUD-01—AUD-06 的實現修復歸相應工作包，完成前保留已知問題標記。

<a id="交付物"></a>

### 交付物

- 首期模型：固定文本模型和 tokenizer revision；訓練與推理使用可互相驗證的源版本。
- 首期設備：具體 Apple 型號／內存、NVIDIA 型號／顯存、系統和驅動。
- 桌面殼與 Python 側進程啓動、退出、崩潰、重啓試驗。
- TV-01：按精確模型、引擎和設備組合記錄真實推理、最小訓練與環境復現。
- TV-02：殼與側進程在最小打包試驗中的啓停、崩潰、重啓、路徑和日誌；不依賴項目數據庫、正式簽名或完整升級。
- TV-03：將 TV-01 產生的同一份實際 LoRA 產物，從 NVIDIA 訓練環境帶到指定 Apple 試用設備，固定基座 revision、模板、目標引擎並獨立加載。若需格式轉換，保存輸入／輸出摘要和轉換步驟；命令行即可，尚不是產品閉環。
- 能力聲明初版、提交快照 schema、任務狀態機和存儲佈局。
- ADR 中需要拍板的選型結論與有證據的替代方案；1.1 範圍重估表。

退出只要求 TV-01—TV-03 及上述文檔記錄。AC-01、AC-12、AC-22、AC-26 等是後續完整驗收追蹤，不能反過來阻塞 M0 試驗工作包完成。跨端不可行時調整目標組合併重跑 TV-03；不能先標記支持再等待 M3 補證。

<a id="停止调整条件"></a>

### 停止／調整條件

若目標模型無法加載、驅動不兼容或打包依賴無法穩定復現，先調整該組合，不繼續在前端標記支持。若 Tauri 宿主延緩核心驗證，可臨時使用本地 Web 界面驗證合同；桌面產品決策單獨記錄。

<a id="5-m1应用和持久化基础"></a>

## 5. M1：應用和持久化基礎

將最終 Demo 轉為正式組件，保持四類入口、模型庫、數據市場、實驗室和 AI 面板。建立項目、任務、數據、模型和作品的數據庫結構；支持安全的文件選擇、導入、元信息和草稿保存。WP-04 在 M1 整理原型與測試的固定項目位置、清單、摘要和復跑命令，保留舊資產；M6 由 WP-30 驗證新成員復跑。

實現任務狀態、事件流、冪等提交和假執行器；覆蓋暫停檢查點失敗、暫停時取消、取消／完成競爭、強制停止及停止狀態未知。計算結果和收集記錄分開，假執行器測試補收不觸發 run／resume，原嘗試終態不改。模型導入計劃同時保存加載方式與信任類別，受限加載失敗不得自動放寬執行能力。假執行器僅用於開發與測試，模式必須顯式，不作為真實模型支持證據。

退出驗收按 GATE-M1：殺掉控制服務後重啓，草稿和索引仍在；開發用執行器狀態可恢復，控制／補收合同負例通過；跨項目後台結果不串入當前項目；文件損壞與磁盤不足有可恢復處理。這裡只驗 M1 子集，不要求真實模型、訓練候選、M4 媒體或 M6 安裝升級已完成。

<a id="6-m2真实推理与参数生效"></a>

## 6. M2：真實推理與參數生效

先完成一個 Apple 本地文本推理適配器和一個 NVIDIA 服務推理適配器。實現模型準備、加載、卸載、輸入處理、流式輸出、取消、結果保存、實際參數記錄和配方重載。

開放經過驗證的思考開關、上下文、輸出上限和採樣參數；KV、前綴緩存和調度先選擇少量可測組合。其餘高級選項保留說明和未驗證狀態，不急於全部開放。模型／策略／引擎／產物格式改變時重新校驗任務模式、素材和配套組件；提交端拒絕舊配置。參數摘要、按鈕旁執行位置和發送範圍統一來自本次已應用配置。

加入“模型默認、低內存、低延遲”三個可解釋預設，綁定已經驗證的組合；應用前展示實際字段差異，取消不改值，不宣稱未經測量的收益。前綴緩存測試納入媒體身份、順序、處理器與預處理參數，未知組合保持關閉。首次使用引導在此形成可操作的語言試用路徑。

退出驗收按 GATE-M2：輸入／輸出 token 預算正確；界面、已應用配置、請求快照、後端實際參數和執行位置一致；配方／預設能說明失效項；斷網本地推理、遠端中斷、取消後資源釋放、只補收不重算通過。

<a id="7-m3训练与评测闭环"></a>

## 7. M3：訓練與評測閉環

實現 SFT + LoRA 的數據檢查、版本化分詞與監督配方、訓練、檢查點、恢復、獨立評測、候選登記和直接試用。檢查多輪、超長、空回答、EOS／PAD、packing 邊界的最終 tokens／labels，統計有效監督 token 並拒絕零監督樣本。增加 QLoRA 或全參數路徑前，先鎖定後端與硬件；不將“LoRA 能跑”視為其他更新方式已完成。

AI 輔助接入真實建議模型，但只開放已定義字段，完成預覽、應用、撤銷與衝突測試。首個內測版本在此階段形成，範圍限定於已經驗收的語言任務和設備。

WP-29 的模型／適配器／文本作品／報告導出子項在 M3 交付，由後端與前端共同承擔：選擇對象、解析依賴、清單、完整性、落盤、取消／失敗恢復和獨立環境使用。這裡不依賴 M6 安裝更新工作。

退出驗收按 GATE-M3：真實數據 → 權重更新 → 獨立產物 → 評測 → 同份產物在目標設備試用及導出；失敗重試保留原任務，收集失敗只補收；檢查點恢復有一致性記錄；AI 無執行權。

<a id="8-m4媒体和工作流"></a>

## 8. M4：媒體和工作流

分別選一個圖片生成／微調組合、一個短視頻組合和一個能完成配音的 TTS 組合；ASR、變聲和音樂按凍結矩陣追加。僅接入 ASR 不能滿足三步工作流的配音出口。每類必須驗證真實文件讀取、真實產物和任務特有參數，不能用文本任務複製頁面替代。

實現“商品圖 → 視頻 → 配音”的結果傳遞、舊結果失效標記、階段重做和整體保存。每次執行、步驟嘗試、輸入版本獨立編號；默認只能使用本輪當前步驟產物，顯式復用舊產物必須記錄來源。先校驗目標佔用，再原子提交推進；失敗不改步驟、輸出或源草稿，重復點擊只推進一次。

WP-29 增加圖片、視頻、音頻作品導出；人工字幕／轉寫修改寫入 WorkRevision，保留原結果和生成配方，重新生成不隱含套用人工修訂。數據市場至少接入一個可控來源，驗證受限訪問流程、版本、下載和原任務返回。

退出驗收按 GATE-M4：兩輪三步真實流程與目標忙碌反例通過；來源鏈、媒體導出和編輯差異完整；圖像、視頻、音頻有對應報告；市場接口不可用時已下載數據仍可使用。

<a id="9-m5专项和多硬件"></a>

## 9. M5：專項和多硬件

按成熟度獨立推進量化、轉換、合併、蒸餾、行為調整。先選擇較小模型和可重復評測集，明確每項的輸入格式和產物，避免建立統一空殼後宣稱全部完成。

AMD／ROCm、Intel／SYCL、OpenVINO／NPU、Core ML／ANE 逐條加入設備矩陣。MTP 與 DFlash 使用已配套的目標模型、組件和版本，完成優化開／關對照。Prefill／Decode 分離若不具備部署條件，作為獨立延後工作包，不阻塞其他優化。

退出驗收按 GATE-M5：每個開放組合都有支持範圍、限制、測試樣本和報告；Core ML 等轉換候選從“候選 → 運行”入口選中可加載引擎，錯誤格式／引擎兩個方向都拒絕；推測策略切換使不匹配準備狀態失效；不能驗證的組合保持未驗證或不支持。

<a id="10-m6稳定化与发布"></a>

## 10. M6：穩定化與發佈

凍結候選版本後執行乾淨機器安裝、升級／回滾、數據庫遷移、備份恢復、長任務、磁盤滿和網絡故障測試。真實模式中不存在預置成功報告、模擬連接捷徑或偽造進度。

按實際支持矩陣編寫用戶手冊和發行說明，附安裝包身份、依賴版本、已知問題、恢復方法和兼容性清單。發佈動作與準備發佈包分別驗收。GATE-M6 匯總凍結範圍內 AC-01—AC-27；用同一候選包完成 5 名目標用戶零資源到首次結果、升級後產物導出、跨端產物鏈和恢復回歸。

審計資產按 E-05 納入固定版本位置並提供清單、摘要和復跑命令，保留原資產；本次文檔修訂不能將仍可復現的 Demo 錯誤標記為產品修復完成。

## 11. 版本建議

<a id="12-依赖与关键路径"></a>

## 12. 依賴與關鍵路徑

關鍵路徑為：能力與快照合同 → 資產／數據庫 → 任務執行與恢復 → 真實推理 → 訓練與產物 → 獨立評測 → 候選試用 → 發佈驗收。

可以交錯推進的工作：數據導入器與前端表單、遠程執行器與本地推理、媒體解碼與專項模型來源核查。不能提前跳過的依賴：沒有固定數據版本不能做公平評測；沒有真實參數映射不能做優化測速；沒有產物完整性不能登記候選；沒有精確設備身份不能宣稱 ANE／ROCm／oneAPI 通過。

<a id="13-进度管理与变更控制"></a>

## 13. 進度管理與變更控制

每周按工作包更新：已完成證據、進行中內容、阻塞、下周交付，不只報告百分比。每個階段結束進行實際任務演示和測試報告評審。

新增模型或優化開關需要一張能力卡和相應測試成本。需求變更同時更新 PRD 編號、工作包、驗收用例和支持矩陣；發現更簡單且滿足目標的實現可以調整方案，但不能刪掉用戶已經確定的完整流程。

<a id="14-估算边界"></a>

## 14. 估算邊界

本計劃沒有取得團隊排班、設備預算或正式上線窗口。開始 M0 後用實際加載、訓練、打包、跨端產物與測試結果重估，並對新增整改及增強逐項列出投入。未完成重估前，1.0 的 19—28 周只作歷史比較。若由單人實施，不能直接沿用上面的日曆週期；應縮減並行工作並以完整閉環為階段單位逐次承諾。
